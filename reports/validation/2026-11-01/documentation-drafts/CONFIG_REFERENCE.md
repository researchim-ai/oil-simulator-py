# Справочник параметров конфигурации

## Сходимость при запуске deck Eclipse

`run_deck(..., sim_overrides={"convergence_profile": "strict"})` — профиль по умолчанию:
CNV `1e-3`, MB `1e-7`, без ослабления по доле порового объёма. Индивидуальные параметры
в `sim_overrides` имеют приоритет над профилем. JSON-режим сохраняет свои прежние настройки.

`convergence_profile="relaxed"` явно выбирает прежние настройки deck (с предупреждением): CNV `1e-2`,
ослабление с первой итерации при доле нарушений ≤3% порового объёма до CNV `1` и MB `1e-6`.
Это отдельный компромисс точности и скорости; его результаты нельзя маркировать как строгую сходимость.
Зацикливание строгого профиля в синтетическом wet-gas тесте исправлено: убрана блокировка смены
первичной переменной после трёх фазовых переключений. Первые 31 сутки теперь проходят за 11 попыток
(~2.5 с CPU), ранее за 100 попыток доходили лишь до 28.95 суток. Проверен также баланс нефти и газа
за 1500 суток на строгих допусках (`tests/test_wet_gas.py`).
Профиль применяется при создании расчёта; при `resume` используются настройки сохранённого решателя.

Сравнение: `scripts/compare_eclipse.py --metric max --all --start-day 360 --end-day 400
--report-json report.json` показывает максимальные ошибки в выбранном окне. JSON содержит также
средние и конечные ошибки, дату пика, абсолютную ошибку в единицах SUMMARY и значения обоих расчётов
для каждой скважины. Нормировка процентов остаётся на масштаб вектора с нижними порогами,
а не на мгновенное значение эталона. Конечная ошибка нормируется на масштаб выбранного окна.
Неопределённые GOR/обводнённость при нулевой добыче и отсутствующие давления узлов сети не считаются
числовыми нулями: отчёт указывает число определённых отсчётов и их последнюю дату. Для полностью
неопределённого вектора выводится предупреждение. NaN дебитов и пластовых давлений остаётся ошибкой.
`--convergence-profile relaxed` явно выбирает старый профиль.

Этот раздел описывает формат файлов `configs/*.json`, используемых для запуска симуляций.  
Документ охватывает **все поддерживаемые параметры** на верхнем уровне и внутри основных блоков: `simulation`, `reservoir`, `fluid`, `wells`.

## 1. Общая структура JSON

```json
{
  "description": "Необязательное текстовое описание кейса",
  "output_filename": "имя_выходного_набора",
  "save_vtk": false,

  "simulation": { ... },
  "reservoir": { ... },
  "fluid": { ... },
  "wells": [ ... ]
}
```

| Параметр            | Тип / значение по умолчанию | Описание |
|---------------------|-----------------------------|----------|
| `description`       | `string`, optional          | Свободный комментарий, отображается в логах. |
| `output_filename`   | `string`, optional (default: timestamp) | Базовое имя каталога и отчётных файлов в `results/`. |
| `save_vtk`          | `bool`, default `false`     | Если `true`, финальное состояние записывается в VTK (`.vtr`). |
| `save_vtk_intermediate` | `bool`, default `false` | Сохранять VTK на промежуточных шагах (каждые `save_interval`). |
| `save_plotly_3d`    | `bool`, default `false`     | Создавать интерактивные 3D визуализации через Plotly (HTML файлы). |
| `simulation`        | `dict`, required            | Настройки временной схемы, решателей и вывода. |
| `reservoir`         | `dict`, required            | Геометрия, пористость, проницаемость, стохастические поля. |
| `fluid`             | `dict`, required            | Начальные условия и модели PVT/относительных проницаемостей. |
| `wells`             | `list`, optional            | Список скважин; если пустой, рассчитывается без источников. |

## 2. Блок `simulation`

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `solver_type` | `"impes"` \| `"fully_implicit"` (default `"impes"`) | Выбор основной схемы. FI требует меньше ограничений по dt, но дороже. |
| `total_time_days` | `float`, default `100.0` | Общая продолжительность расчёта. |
| `time_step_days` | `float`, default `1.0` | Базовый шаг по времени. |
| `max_time_step_attempts` | `int`, default `5` | Количество попыток уменьшить шаг, если решение не сходится. |
| `dt_reduction_factor` | `float`, default `2.0` (`1.5` в FI) | Во сколько раз уменьшать шаг при неудаче. |
| `dt_increase_factor` | `float`, default `1.25` (`1.5` в FI) | Лимит роста шага при успехе. |
| `use_cuda` | `bool`, default `false` | Разрешает перенос данных на GPU (актуально и для FI). |
| `pressure_solver` | `"cg"` \| `"amg"`, default `"cg"` | Решатель для этапа давления. |
| `pressure_float64` | `bool`, default `false` | Переводит систему давления в float64 перед CG. |
| `cg_tolerance` | `float`, default `1e-6` | Допуск CG; также используется как fallback для AMG. |
| `cg_max_iter` | `int`, default `500` | Максимальное число итераций CG. |
| `global_rate_scale` | `float`, default `1.0` | Масштабирование всех заданных дебитов (удобно для чувствительности). |
| `max_substeps` | `int`, default `20` | Верхний лимит подшагов насыщенности (IMPES). |
| `max_saturation_change` | `float`, default `0.05` | Максимальное изменение насыщенности за подшаг (IMPES). |
| `cfl_safety_factor` | `float`, default `0.9` | Если рекомендуемый `dt` после CFL-мониторинга меньше `cfl_safety_factor · dt`, шаг повторяется с понижением. Значение зажато в диапазоне `[0.1, 0.99]`. |
| `cfl_retry_cap` | `float`, default `50.0` | Ограничивает агрессивность CFL: повторный запуск выполняется только если `rat_max < max_substeps · cfl_retry_cap`. При больших нарушениях шаг считается принудительно зафиксированным (с клампами). |
| `use_capillary_potentials` | `bool`, default `false` | Включает апстрим по полным потенциалам $p \pm p_c \pm ρgΔz$. При `true` рекомендуется уменьшить `time_step_days`. |
| `save_interval` | `int`, default `10` | Шаг сохранения промежуточных PNG в `results/.../intermediate`. |
| `animation_fps` | `int`, default `5` | Частота кадров итоговой анимации (при `save_interval < num_steps`). |
| `write_full_arrays_txt` | `bool`, default `false` | Записывать ли полные 3D-массивы в текстовый отчёт (может быть очень объёмно). |
| `save_npz` | `bool`, default `true` | Сохранять ли финальные поля в `npz`. |
| `debug_component_balance` | `bool`, default `false` | Включает детальный лог компонентного баланса. |
| `debug_log_path` | `string`, optional | Пользовательский путь для debug-лога; если не указан, создаётся `results/component_debug_*.log`. |
| `mass_balance_tolerance` | `float`, default `1e-3` | Относительный допуск для проверки массового баланса на шаге. Порог = `max(mass_balance_tolerance_abs, tol · (|in|+|out|+|accum|))`. |
| `mass_balance_tolerance_abs` | `float`, default `1e-2` | Абсолютный допуск (кг) для проверки баланса. |

При выполнении шага IMPES симулятор автоматически:

- оценивает требуемый `dt` по CFL (по величине подшагов насыщенности) и при необходимости повторяет шаг с уменьшенным `dt`;
- логирует choke по насыщенности, срабатывания `bhp_min`, а также факты троттлинга по лимитам `wopr/wlpr/wgpr/liqr`;
- проверяет массовый баланс по каждой фазе и выводит предупреждение, если остаток превышает заданные пороги.

### 2.1 Параметры AMG (`simulation.amg`)

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `theta` | `float`, default `0.25` | Порог сильных связей (Classical RS). |
| `max_levels` | `int`, default `10` | Максимальная глубина иерархии. |
| `coarsest_size` | `int`, default `200` | Целевой размер самого coarse-уровня. |
| `tol` | `float`, default `1e-6` | Допуск по резидуалу для V-циклов. |
| `max_cycles` | `int`, default `20` | Максимальное число V-циклов. |
| `device` | `"auto"` \| `"cpu"` \| `"cuda"` | Где строить иерархию; `"auto"` выбирает GPU при наличии. |
| `mixed_precision` | `bool`, default `false` | Перевод уровней ≥ `mixed_start_level` в float32. |
| `mixed_start_level` | `int`, default `2` | Уровень, с которого применять float32. |
| `cpu_offload` | `bool`, default `false` | Перенос уровней ≥ `offload_level` на CPU после сборки. |
| `offload_level` | `int`, default `3` | Первый уровень для offload. |

> Если `mixed_precision` или `cpu_offload` включены, параметры остаются опциональными: по умолчанию решение выполняется полностью на GPU в float64.

### 2.2 Дополнительные параметры для fully implicit

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `fim_model` | `"auto"` \| `"oil_water"` \| `"blackoil"`, default `"auto"` | Модель FIM. `auto` включает трёхфазный black-oil, если задана PVT-таблица, начальная `s_g > 0`, есть газовая нагнетательная или добывающая с `surface_phase: "gas"`. |
| `newton_max_iter` | `int`, default `15` | Максимальное число итераций Ньютона на подшаг. |
| `newton_tol_cnv` / `newton_tol_mb` | `float`, default `1e-3` / `1e-7` | Локальный (CNV) и глобальный (MB) критерии сходимости. |
| `newton_tol_well_rate` / `newton_tol_well_bhp` | `float`, default `1e-5` / `10` Па | Точность выполнения уставок скважин. |
| `newton_ds_max`, `newton_dp_max_rel`, `newton_dp_max_abs_mpa`, `newton_dbhp_max_rel` | default `0.2`, `0.3`, `2.0`, `1.0` | Ограничение поправок Ньютона по ячейкам. |
| `newton_drs_max_rel` | default `0.2` | Black-oil: ограничение поправки Rs в недонасыщенной ячейке (доля от максимального Rs таблицы). |
| `linear_restart`, `linear_max_restarts` | default `50`, `4` | Размер подпространства FGMRES и число рестартов. |
| `linear_tol_min`, `linear_tol_max`, `linear_accept_rel_res` | default `1e-6`, `1e-2`, `0.1` | Допуск неточного Ньютона и порог отказа СЛАУ. |
| `amg_rebuild` | `"step"` \| `"iteration"`, default `"step"` | Когда строить иерархию AMG заново (иначе — только обновление значений). |
| `cpr_smoother_sweeps` | `int`, default `1` | Число проходов блочного Якоби во второй ступени CPR. |
| `newton_target_iter`, `dt_target_dsw` | default `6`, `0.2` | Цели адаптивного шага по времени. |
| `dt_increase_factor`, `dt_reduction_factor` | default `2.0`, `2.0` | Максимальный рост и дробление шага. |
| `dt_control` | `"basic"` \| `"opm"`; для deck Eclipse `"opm"` | `opm` — PID по относительному изменению решения (`dt_pid_tol`, 0.1) и целевому числу итераций (`newton_target_iter`, 8), рост ≤ 3×, после отказа ≤ 2×, дробление `dt_restart_factor` (0.33), как в OPM Flow. |
| `initial_time_step_days`, `min_time_step_days`, `max_time_step_days` | default — отчётный шаг, `1e-6`, отчётный шаг | Границы шага по времени (`time_step_days` — отчётный интервал). |
| `max_time_step_attempts` | `int`, default `8` | Максимум дроблений шага подряд. |
| `debug` | объект | Режим отладки решателя, см. `fim_technical_details.md`. |

Параметры скважин для FIM: `perforations`, `skin`, `well_index`, `bhp_min`, `bhp_max`, `surface_phase` (`liquid` | `oil` | `water` | `gas`), `injected_phase` (`water` | `gas`), `ramp_days` — см. `fim_technical_details.md`, разделы 2 и 9. Дебиты в FIM всегда поверхностные; `rate_type: "reservoir"` в FIM не поддерживается.

В black-oil `stopped: true` задаёт нулевой поверхностный расход с открытыми перфорациями:
внутренний переток сохраняется, каждый компонент имеет нулевой нетто-расход.
`control_type: "shut"` отключает соединения с пластом. При импорте deck состояния STOP и
нулевые уставки открытой скважины преобразуются в остановку с внутренним перетоком.
`fim_model: "auto"` выбирает black-oil и для остановленных скважин; явная двухфазная
`oil_water` с `stopped: true` отклоняется как неподдерживаемая комбинация.

При импорте SWOF/SGOF применяется `TOLCRIT` (по умолчанию `1e-6`): значения ОФП
не выше порога обнуляются до интерполяции и определения критических насыщенностей.
Капиллярные давления этим порогом не изменяются.

`connection_order` задаёт порядок перфораций для гидростатики black-oil: `INPUT` (по умолчанию для JSON,
порядок `perforations`), `TRACK` (от устья по ближайшим I/J, при равенстве — по разности глубин),
`DEPTH` (по глубине). В deck по умолчанию используется `TRACK`; `COMPORD` меняет правило по расписанию.
Гидростатический напор суммируется вдоль этого порядка, поэтому подъём участка ствола даёт отрицательный вклад.

При импорте Eclipse deck пропущенная или отрицательная опорная глубина `WELSPECS`
берётся из первого первоначально определённого соединения с учётом `COMPORD`,
включая закрытые соединения. Позднейшие перфорации и изменения порядка не сдвигают
эту глубину. Явная глубина сохраняется; для MSW применяется глубина верхнего сегмента.
Это отличается от значения по умолчанию в ручной JSON-конфигурации: там по-прежнему
используется минимальная глубина перфораций.

Из `TUNING` применяются параметры времени `TSINIT`, `TSMAXZ`, `TSMINZ`, `TSFMAX`, `TSFCNV`, `TMAXWC` и `TRGTTE`.
Они сохраняются и обновляются по расписанию; явно заданный `TSINIT` перезапускает выбор подшага.
Явные `sim_overrides` имеют приоритет над deck. Остальные явно заданные поля `TUNING` пока вызывают
предупреждение; допуски CNV/MB и локальное ослабление по-прежнему определяет `convergence_profile`.
Лимит `max_time_step_days` соблюдается и при объединении хвоста отчётного интервала.

В `dt_control: "opm"` относительное изменение — отношение сумм квадратов
изменений давления и всех трёх насыщенностей к сумме квадратов текущего
состояния (без квадратного корня). Это соответствует OPM 2026.04. При загрузке
старого checkpoint история PID с прежней формулой сбрасывается; физическое
состояние сохраняется. Новый формат истории переносится через перезапуск.
Критерии CNV/MB контролируют решение нелинейной системы, а не погрешность
интегрирования по времени: точность фронта проверяется уменьшением подшага.
`TMAXWC` задаёт первый подшаг после изменения управления или соединений скважин
(`time_step_after_well_event_days` в `sim_overrides`); ноль отключает этот перезапуск.

## 3. Блок `reservoir`

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `dimensions` | `[Nx, Ny, Nz]`, **обязателен** | Число ячеек вдоль каждой оси. |
| `grid_size` | `[Δx, Δy, Δz]`, обязательный базовый шаг (м) | Используется как усреднение и fallback для `grid`. |
| `porosity` | `float` \| массив \| `.npy/.npz`, default `0.2` | Фиксированная или пространственная пористость. |
| `permeability` | `float` \| массив \| `.npy/.npz`, default `100.0` | Горизонтальная проницаемость в мД. |
| `k_vertical_fraction` | `float`, default `0.1` | Отношение $k_v / k_h$ (если нет независимого поля). |
| `c_rock` | `float`, default `1e-5` (1/МПа) | Сжимаемость породы. |

### 3.1 Подблок `reservoir.grid` (опционально)

| Параметр | Тип | Описание |
|----------|-----|----------|
| `dx`, `dy`, `dz` | массив длиной `Nx`, `Ny`, `Nz` | Неравномерный шаг вдоль оси (в метрах). |
| `x_nodes`, `y_nodes`, `z_nodes` | массив длиной `N+1` | Альтернатива: координаты узлов. Разности вычисляются автоматически. |

Можно комбинировать: например, задать `dx`, но использовать `y_nodes`. Если подблок отсутствует, сетка равномерна.

> ⚠️ Fully implicit решатель в текущей версии поддерживает только равномерные сетки (`grid` не задан или все шаги одинаковы).

### 3.2 Подблок `reservoir.stochastic` (опционально)

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `seed` | `int`, default `0` | Базовый seed генератора. |
| `porosity` | `dict`, optional | Генерация поля пористости. |
| `permeability` | `dict`, optional | Генерация поля проницаемости (в мД). |

Внутри `porosity`/`permeability` доступны:

| Ключ | Тип / default | Значение |
|------|---------------|----------|
| `mean` | `float`, default текущее среднее | Среднее значение поля. |
| `std` | `float`, default текущее σ или 0.01 | Стандартное отклонение. |
| `corr_length` | `float`, default `0.0` | Корреляционный радиус (в ячейках). При наличии SciPy используется `gaussian_filter`. |
| `distribution` | `"normal"` или `"lognormal"`, default `"normal"` | Форма распределения. |
| `log_mean`, `log_std` | `float`, optional (lognormal) | Параметры лог-нормального распределения. |
| `min`, `max` | `float`, optional | Жёсткие границы (для пористости). |
| `min_md`, `max_md` | `float`, optional | Границы проницаемости в миллидарси. |
| `k_vertical_fraction` | `float`, optional (только для permeability) | Переопределяет вертикальное отношение для сгенерированного поля. |
| `seed` | `int`, optional | Отдельный seed; если не задан, используются `seed`, `seed+1`. |

## 4. Блок `fluid`

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `pressure` | `float`, default `20.0` (МПа) | Начальное пластовое давление. |
| `s_w`, `s_g` | `float`, defaults `0.2`, `0.0` | Начальные насыщенности воды и газа. Нефть берётся как `1 - s_w - s_g`. |
| `mu_oil`, `mu_water`, `mu_gas` | `float`, defaults `1.0`, `0.5`, `0.02` (сП) | Вязкости при отсутствии PVT. |
| `rho_oil`, `rho_water`, `rho_gas` | `float`, defaults `850`, `1000`, `1.0` (кг/м³) | Плотности при стандартных условиях. |
| `c_oil`, `c_water`, `c_gas`, `c_rock` | `float`, defaults `1e-5`, `1e-5`, `1e-3`, `1e-5` (1/МПа) | Сжимаемости фаз и породы (используются без PVT). |
| `pvt_path` | `string`, optional | Путь к JSON или Eclipse/CMG deck. При указании автоматически загружаются PVT и таблицы SWOF/SGOF. |
| `pvt` | `dict`, optional | Альтернатива: словарь с полями `pressure_MPa`, `Bo`, `Bw`, `Bg`, `mu_o_cP`, ... (см. `tests/test_deck_loader`). |

### 4.1 Relative permeability (`fluid.relative_permeability`)

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `model` | `"corey"` \| `"stone2"` \| `"table"` (default `"corey"`) | Выбор модели. |

**Corey/Stone II параметры (используются по мере необходимости):**

- `sw_cr`, `so_r`, `sg_cr` — критические/остаточные насыщенности (`default sw_cr=0.2, so_r=0.2, sg_cr=0.0`).
- `nw`, `no`, `ng` — степенные показатели кривых (по умолчанию `2.0`).
- `ko_end_w`, `ko_end_g` — конечные значения нефтефазной проницаемости по воде/газу (для Stone II).
- `now`, `nog` — степени нефтефазных ветвей (Stone II; default совпадает с `no`/`ng`).
- `krw_end`, `krg_end` — конечные значения водной и газовой кривой (Corey).

**Табличный режим (`model: "table"`):**

- `path` — путь к deck-файлу или `.json`. Требуются секции **SWOF** (вода–нефть) и/или **SGOF** (газ–нефть).
- Если PVT загружается из того же deck, отдельный `path` можно не указывать.
- Симулятор автоматически строит производные `dkr/dS` и кривые Pc из предоставленных данных.

### 4.2 Capillary pressure

| Блок | Параметры | Описание |
|------|-----------|----------|
| `capillary_pressure` | `pc_scale`, `pc_exponent`, `pc_threshold` (defaults `0`, `1.5`, `0.01`) | Давление между водой и нефтью (степенная зависимость). |
| `capillary_pressure_og` | `pc_scale`, `pc_exponent` (defaults `0`, `1.5`) | Аналогично для пары нефть–газ. |

При ненулевом `pc_scale` рекомендуется включить `simulation.use_capillary_potentials`, чтобы потенциалы учитывали Pc при апстриминге.

## 5. Блок `wells`

Каждый элемент списка описывает отдельную скважину.

| Параметр | Тип / default | Описание |
|----------|---------------|----------|
| `name` | `string` | Уникальное имя. |
| `type` | `"injector"` \| `"producer"` | Направление потока. |
| `i`, `j`, `k` \| `coordinates` | Целочисленные индексы ячейки (оба формата поддерживаются). |
| `radius` | `float` (м) | Радиус ствола (используется в модели Писмана). |
| `control_type` | `"rate"` \| `"bhp"` | Режим управления. В старом формате — `control.type`. |
| `control_value` | `float` | Для `rate`: дебит в м³/сут; для `bhp`: забойное давление в МПа. Старый формат `control.value`. |
| `rate_type` | `"reservoir"` \| `"surface"`, default `"reservoir"` | Относится только к режиму `rate`. |
| `surface_phase` | `"oil"` \| `"water"` \| `"gas"` \| `"liquid"` | Требуется если `rate_type="surface"` и скважина — producer. |
| `injected_phase` | `"water"` \| `"gas"` (default `"water"`) | Для инжекторов c `rate_type` `'surface'`. |
| `limits` | `dict`, optional | Поверхностные лимиты (м³/сут). Поддерживаются ключи `wopr` (oil), `wlpr` (water), `wgpr` (gas), `liqr` (oil+water). |
| `bhp_min` | `float` (МПа), optional | Минимально допустимый BHP (для продакшн-скважин под `rate`). Если давление в ячейке ниже, дебит автоматически тюнингуется. |

> В режиме `surface` симулятор самостоятельно переводит дебит в пластовые условия с использованием текущих $B\_\alpha$, $R_s$, $R_v$.

## Физическая жидкостная сеть

Отдельный стационарный изотермический решатель `surface.LiquidNetwork` использует
JSON с `model: "incompressible_liquid"`; пример — `configs/surface_liquid_ring.json`.
Это самостоятельный расчёт труб, ещё не связанный автоматически с black-oil.

```bash
python scripts/run_surface_network.py configs/surface_liquid_ring.json --output /tmp/surface.json
python scripts/run_surface_network.py configs/surface_liquid_ring.json --initial-state /tmp/surface.json
```

В `fluid` обязательны `density_kg_m3` и динамическая `viscosity_pa_s`;
`vapor_pressure_pa` по умолчанию равен нулю. Плотность и вязкость постоянны.
В `nodes` задаются уникальное `name`, `elevation_m` (по умолчанию 0),
`source_mass_rate_kg_s` (по умолчанию 0) и необязательное **абсолютное**
`pressure_pa`. Положительный источник подаёт массу в сеть, отрицательный отбирает.
Каждая связная часть открытой сети требует хотя бы одного узла заданного давления.

В `pipes` обязательны уникальное `name`, узлы `start`/`end`, положительные
`length_m` и `diameter_m`. Необязательные поля: `roughness_m` (0),
`minor_loss_coefficient` (0), `open` (true). Длина не меньше перепада отметок.
Положительный расход направлен от start к end; обратный поток допускается.
Закрытая труба имеет нулевой расход и не связывает давления.

Используются Darcy–Weisbach, точный ламинарный предел и Swamee–Jain в турбулентном
режиме с гладким переходом Re=2000–4000. Относительная шероховатость ограничена 0.05.
Закон трения и переход сверены с [алгоритмами EPANET 2.2](https://usepa.github.io/EPANET2.2/12_analysis_algorithms.html).
Эталон `tests/data/surface/epanet_22_ring.json` получен из исходного релиза EPANET
2.2: содержит SHA256 архива, исходные параметры, независимые напоры и расходы.
Для воспроизведения с локально собранной библиотекой EPANET используйте
`python scripts/check_surface_epanet.py .scratch/epanet_220_20261031`
(каталог содержит `build/lib/libepanet2.so` и `source_manifest.json`).
Библиотека собирается из тега `v2.2` репозитория OpenWaterAnalytics/EPANET:
`cmake -S EPANET-2.2 -B build -DBUILD_TESTS=OFF -DBUILD_PY_LIB=OFF -DCMAKE_BUILD_TYPE=Release`,
затем `cmake --build build --parallel 2`. Манифест источника хранит поля `url`,
`sha256`, `version` (как в сохранённом эталоне); обычные тесты используют эталон
и не требуют установки EPANET.
На этом примере различие расходов < 3.5e-7 кг/с, напоров < 0.015 м;
константы гравитации и округление местных потерь в EPANET отличаются.

Результат содержит давления, массовые/объёмные расходы труб и
`boundary_mass_rates_kg_s`: дополнительный обмен с окружением, необходимый для
поддержания давления. Положительный граничный расход подаёт массу в сеть.
В каждом узле сумма источника и граничного обмена равна чистому оттоку по трубам.
Возвращаются невязки массы и давления, диссипация и ошибка баланса механической
мощности. Это не тепловой энергетический расчёт.

API `solve()` принимает переопределения источников и граничных давлений по именам
узлов и предыдущий `NetworkResult` как начальное приближение. Допуски по умолчанию:
давление 1e-3 Па, масса 1e-8 кг/с, до 60 итераций. Недостижение допуска или давление
не выше давления пара вызывает явную ошибку; давление не обрезается.
Массовые расходы нельзя подменять суммой поверхностных объёмов нефти/воды/газа.
Газ, фазовое равновесие, многофазное удержание, насосы, компрессоры и сепараторы
в этом режиме пока не моделируются. Существующая VFP-сеть остаётся отдельным
поддерживаемым режимом связи скважин с поверхностью.

### Насосы в физической жидкостной сети

`pumps` — необязательный список ветвей; имена уникальны среди труб и насосов.
Пример: `configs/surface_liquid_booster.json`.

```bash
python scripts/run_surface_network.py configs/surface_liquid_booster.json --output /tmp/booster.json
```

Обязательны `name`, `start` (вход), `end` (выход), `shutoff_head_m`,
`curve_coefficient_s2_m5` и `max_flow_m3_s`. Характеристика центробежного насоса:
`H(q,s) = s² H0 − a q²`, где H — напор в метрах перекачиваемой жидкости,
q — м³/с, s — относительная скорость. Коэффициент a имеет размерность с²/м⁵.
`max_flow_m3_s` задаётся при номинальной скорости; рабочий предел равен s·q_max.
Заданный диапазон не должен заходить в область отрицательного напора.
Подобие при изменении скорости соответствует [модели насосных характеристик EPANET](https://usepa.github.io/EPANET2.2/3_network_model.html).

Необязательны: `speed_ratio` (1, строго больше нуля), `efficiency` (0.75,
в интервале (0,1]), `open` (true), `max_shaft_power_w`, `npsh_required_m`,
`inlet_diameter_m`. Для проверки NPSH обязательно задать диаметр входного патрубка.
NPSH_available = (p_in_absolute − p_vapor)/(ρg) + v_in²/(2g),
где v_in = q/A_in. Порог NPSH задаётся для текущего режима: автоматически с
изменением скорости он не масштабируется. Давление входного узла трактуется
как статическое давление во входном патрубке. Характеристика H относится к
полному напору; разность скоростных напоров между патрубками в этом этапе
полагается нулевой (равные проходные сечения).

Насос решается одновременно с трубами и давлениями узлов, с аналитической
производной характеристики. Рабочая точка определяется сетью; переданная жидкости
гидравлическая мощность P_h = ρgqH, мощность на валу P_s = P_h/η.
КПД постоянный; моторные, механические и холостые потери отдельно не заданы.
В частности, нулевой расход даёт нулевую расчётную мощность, что не является
моделью реального потребления насоса на закрытую задвижку.

Обратное течение через работающий насос, превышение максимального расхода,
мощности или недостаточный NPSH вызывают `EquipmentOperatingError`.
Ограничения расхода, мощности и NPSH проверяют допустимость рабочей точки;
автоматических защит двигателя и переключения резервного агрегата пока нет.
Необязательный обратный клапан и ограниченный регулятор скорости описаны ниже.
Для Ньютона используется гладкое продолжение кривой в отрицательные расходы;
такой режим не выдаётся как допустимый результат. `open: false` полностью
закрывает ветвь, в том числе исключает пассивный проток через остановленный насос.

Результат содержит отдельные `pump_mass_rates_kg_s`, `pump_volume_rates_m3_s`,
`pump_equation_residuals_pa`, `pump_hydraulic_power_w`, `pump_shaft_power_w` и,
если задан диаметр, `pump_npsh_available_m`. Закрытые насосы имеют нулевые расходы;
уравнение характеристики и мощность для них не рассчитываются.
Баланс механической мощности теперь учитывает гидравлическую работу насосов:
граничная мощность + работа насосов − диссипация труб. Валовые потери в этот
гидравлический баланс не входят; тепловой расчёт отсутствует.

API `solve(pump_speed_ratios={name: speed}, pump_status={name: bool})`
позволяет менять режимы без изменения исходного объекта сети; сохраняются
проверки связности и граничных условий. Результат можно использовать как
начальное приближение следующего режима. Старые результаты без `pump_*`
полей читаются для сетей без насосов.

Независимый эталон — `tests/data/surface/epanet_22_booster.json`.
Воспроизведение: `python scripts/check_surface_epanet.py .scratch/epanet_220_20261031
--config configs/surface_liquid_booster.json --max-flow-error-kg-s 0.001`
(команда одной строкой). На данном примере расхождение расходов с EPANET 2.2 —
0.0001594 кг/с (около 0.0044%), напоров — 0.00159 м. Допуски эталонного теста
учитывают разные гравитационные/округлённые гидравлические константы.

### Обратные клапаны и автоматические состояния

`check_valve: true` в трубе или насосе запрещает обратный поток; по умолчанию
false для совместимости с существующими моделями. Работающий насос с таким
клапаном блокируется, если его напора недостаточно против давления сети, и
может снова начать подачу после изменения давления или скорости.
Это гидравлическое состояние «насос + обратный клапан», а не защёлкивающаяся
электрическая защита двигателя. Состояние пересчитывается для каждого режима.

Решается условие дополнительности q ≥ 0, d ≤ 0, q·d = 0, где
`d = H_start − H_end − loss(q)` в единицах давления. В закрытом состоянии
расход строго нулевой, перепад давления поддерживается клапаном; искусственная
утечка или большое фиктивное сопротивление не вводятся. Для насоса при
открытии из нулевого расхода используется стартовая секущая в линеаризации,
а невязка остаётся на точной характеристике и проверяется исходными допусками.

`branch_states` возвращает `open`, `closed` (ручное отключение) или `blocked`
(автоматически закрытый обратный клапан). `check_valve_driving_pressure_pa`
содержит d. Невязка `*_equation_residuals_pa` для такой ветви относится к
условию дополнительности, а не к равенству давлений на закрытом клапане.
Заблокированные насосы не получают рабочую мощность/NPSH в результате.
Они имеют нулевой гидравлический расход; потребление двигателя на холостом
ходу не моделируется. Если закрытие изолирует часть сети без заданного давления,
решатель не назначает ей произвольное давление и выдаёт ошибку.

Пример: `configs/surface_parallel_pumps.json`. Сильный насос работает, слабый
блокируется противодавлением без обратного потока. Независимый эталон
`tests/data/surface/epanet_22_parallel_pumps.json` подтверждает расходы и состояния
EPANET 2.2: различие расходов < 2.3e-5 кг/с, напоров < 0.00014 м.
В эталоне сохранено предупреждение EPANET 4 о недостаточном напоре насоса;
его статус CLOSED проверяется отдельно, предупреждение не скрыто.

### Регулирование скорости по давлению

`surface.PumpPressureControl` управляет одним открытым насосом по абсолютному
давлению одного узла без заданного граничного давления. Пример спецификации —
`configs/surface_pressure_control.json`.

```bash
python scripts/run_surface_network.py configs/surface_liquid_booster.json --pressure-control configs/surface_pressure_control.json --output /tmp/regulated.json
```

Поля: `pump`, `node`, `target_pressure_pa`, положительные `min_speed_ratio` и
`max_speed_ratio` (min < max); необязательные `pressure_tolerance_pa` (1 Па),
`max_evaluations` (50). Между пределами требуется непрерывная неубывающая
характеристика давления по скорости. Регулятор решает полную сеть на границах
и методом бисекции уточняет скорость; проверяет порядок рассчитанных давлений.
Это внешний стационарный регулятор, без динамики двигателя/PID и оптимизации
совместной работы нескольких насосов.

Результат содержит `network` (обычный результат сети), `speed_ratio`,
`pressure_error_pa`, `evaluations` и `status`: `target`, `min_speed` или
`max_speed`. Последние два состояния означают допустимую гидравлическую рабочую
точку с **недостигнутым** заданием давления, а не ложную сходимость регулятора.
Предел числа вычислений вызывает ошибку. Ошибки мощности/NPSH/расхода передаются
наружу; допустимый по этим ограничениям диапазон скорости должен задать пользователь.
Регулятор не ищет автоматически безопасную границу внутри недопустимого диапазона.

`--initial-state` принимает и обычный результат сети, и результат регулятора;
из второго используется поле `network`. Это начальное приближение гидравлики,
а не сохранение динамического состояния регулятора. Исходная сеть не изменяется.

### Табличные характеристики насосов

`head_curve`, `efficiency_curve`, `npsh_curve` — необязательные объекты с массивами
`flow_m3_s` и `values`. Расходы относятся к номинальной скорости; ось строго
возрастает, начинается с нуля и покрывает `max_flow_m3_s`. Не менее двух точек,
только конечные числа. Интерполяция линейная, с точной производной каждого
отрезка; на узле используется правый отрезок. Карты сохраняются в JSON.

`head_curve.values` задаёт напор в метрах жидкости: значения неотрицательные,
строго убывают, первое совпадает с `shutoff_head_m`. При заданной карте она
заменяет квадратичную характеристику; `curve_coefficient_s2_m5` сохраняется
в схеме для совместимости, но в расчёте напора не используется.
Номинальная карта преобразуется как H(q,s)=s²H_nom(q/s). Продолжение за край
карты разрешено только для промежуточных итераций Ньютона; результат проверяется
по номинальному диапазону расхода, масштабированному скоростью.

`efficiency_curve.values` — доли (0,1], η(q,s)=η_nom(q/s). Карта заменяет
постоянный `efficiency`. `npsh_curve.values` — метры, значения неотрицательные;
требуется `inlet_diameter_m`. Принято приближённое подобие
NPSHr(q,s)=s²NPSHr_nom(q/s). При одновременно заданном постоянном пороге
`npsh_required_m` берётся максимум постоянного и табличного требований.
Это приближение подобия, не расчёт кавитационного течения; вне области подобия
нужны измеренные карты при разных скоростях.

Результат теперь содержит `pump_efficiencies`, `pump_head_gains_m`,
`pump_npsh_required_m`, `pump_npsh_margin_m` (available − required).
Для закрытых/заблокированных агрегатов рабочие характеристики не выдаются.
Пример с картами и дросселем: `configs/surface_mapped_pump_valve.json`.
Эталон `tests/data/surface/epanet_22_mapped_pump_valve.json` получен EPANET 2.2:
различие массовых расходов < 3.3e-14 кг/с, напоров < 0.008 м,
мощность 392.266 Вт против 392.093 Вт. Сравнение относится к данному примеру;
NPSH в EPANET не сверялся, он проверен отдельными расчётными задачами.

### Дроссели и управление открытием

`valves` — отдельный список ветвей `ThrottleValve`, с уникальными среди всех
ветвей именами. Обязательны `name`, `start`, `end`, `diameter_m`.
Необязательны: `discharge_coefficient` (0.62, 0 < Cd ≤ 1), `opening` (1,
0 ≤ opening ≤ 1), `open` (true), `check_valve` (false).

Открытие означает **долю проходной площади**, не процент хода реального привода:
A = opening·πD²/4. Уравнение Δp = ρq|q|/(2(Cd A)²) включено в общую систему
с аналитической производной. Это жидкостное несжимаемое некритическое течение
с постоянным Cd; газовое/двухфазное критическое истечение, вскипание и восстановление
давления в сечении vena contracta не рассчитываются. Следует использовать
модель только в некавитирующей области; давление выше давления пара в узлах
не является самостоятельным доказательством отсутствия кавитации внутри арматуры.

`opening: 0` и `open: false` полностью закрывают ветвь, без фиктивной утечки.
API `solve(valve_openings={name: opening})` не меняет исходную сеть и совместим
с переопределениями скоростей насосов и начальным приближением.
Выходные поля: `valve_mass_rates_kg_s`, `valve_volume_rates_m3_s`,
`valve_equation_residuals_pa`, `valve_dissipation_w`. Диссипация дросселей
включена в баланс механической мощности.

### Компонентные потоки и идеальная black-oil сепарация

`surface.ComponentStream(oil_m3_s, water_m3_s, gas_m3_s)` хранит неотрицательные
расходы **стандартных компонентов**. Газ включает свободный и растворённый газ.
Это не сумма объёмов физических фаз при давлении сепаратора. Стандартные условия
и плотности должны совпадать с условиями входных скважинных/PVT-данных.
`StockDensities` задаёт `oil_kg_m3`, `water_kg_m3`, `gas_kg_m3`.
`mix`, `split`, `from_mass_rates`, `mass_rates` и `component_balance`
обеспечивают смешение, пропорциональное деление и массовый учёт компонентов.
Отрицательные расходы (например, нагнетание) в производственный поток не подставляются.

`BlackOilSeparator(name, pressure_pa, pvt, densities)` использует существующий
`PVTTable`: `pressure_MPa`, `Bo`, `Bw`, `Bg`, `Rs_m3m3` и остальные обязательные
поля стандартной PVT-схемы. Давление сепаратора задаётся в Па, в адаптере PVT
переводится в МПа. Область таблицы проверяется до вызова интерполяции: за краями
нет ни экстраполяции, ни неявного удержания крайнего значения.

Поддержан идеальный изотермический фазовый разделитель без уноса/эмульсий:
Rs_eff = min(Rs_sat(p), Qg_component/Qo_component),
газ в нефтяном выходе = Rs_eff·Qo_component, остальной газ — газовый выход,
вода целиком — водный выход. Для нефти без свободного газа требуется покрывающая
давление и Rs расширенная таблица PVTO; насыщенный Bo не заменяет недонасыщенный.
Все выходы остаются компонентными потоками. Объёмы физических фаз вычисляются
через соответствующие Bo/Bw/Bg и выдаются отдельно; плотности фаз следуют из
массы компонентов в каждой фазе и её объёма.

Rv ≠ 0 отклоняется явно, включая используемые расширенные PVTO-таблицы.
Фазовое равновесие нефть–газ с испарением нефти, EOS, температура, энтальпия,
нагрев/охлаждение при сбросе давления, унос, конструкция и размеры аппарата,
динамика уровней и времени пребывания не входят в эту модель.
`run_separator_train` проводит нефтяной выход через ступени со строго убывающим
давлением; свободный газ и воду каждой ступени отводит отдельно и суммирует.
Учитывается газ, остающийся растворённым в конечном нефтяном продукте.
Проверяются балансы трёх компонентов, а не объёмов при разных давлениях.

### Ограничения, отчёт нарушений и пример площадки

`FacilityLimit(name, metric, unit, minimum=None, maximum=None)` задаёт нижнюю
и/или верхнюю границу именованной величины. `evaluate_limits` требует наличие
метрики, совпадение единиц и конечное значение; неизвестная величина не превращается
в успешную проверку. Отчёт содержит фактическое значение, границы, величину
превышения/недостатка в тех же единицах и `passed` для каждого ограничения.
`feasible` — итог всех ограничений, `violations` — полный список нарушений.
Это оценка пропускной способности и нагрузок, а не автоматическое перераспределение
добычи или изменение уставок для выполнения ограничений.

Сквозной пример (показательные синтетические PVT, не настроенные данные Norne):

```bash
python scripts/run_surface_facility.py configs/surface_facility.json --output /tmp/facility.json
python scripts/run_surface_facility.py configs/surface_facility.json --initial-state /tmp/facility.json --output /tmp/facility_restart.json
```

Поля конфигурации: `stock_densities`, список `feeds`, общая `pvt`, список
`separator_stages` (name, pressure_pa), `water_network`, `water_feed_node`, `limits`.
Два потока поступают на три ступени сепарации (5, 1 и 0.1 МПа), отделённая вода
передаётся в сеть с насосом по картам и регулируемым дросселем.
Нефтяной/газовый продукт учитывается компонентно, их экспортная гидравлика отсутствует.

Связь отделённой воды с сетью — **заданный массовый отвод через идеальный регулятор
уровня/расхода и сброс давления**. Давление входа в водяную сеть вычисляется сетью
и не должно превышать давление водоотвода первой ступени. Мощность идеального
сброса Qwater·(p_separator − p_network) выдаётся отдельно. Плотность воды сети
должна совпадать с плотностью отделённой воды; допускается один узел заданного
давления, дополнительные источники воды не допускаются. Это позволяет проверить
передачу массы без скрытого добавления воды через другую границу. Общая динамическая
система «скважина–сепаратор–уровень–арматура» пока не решается.

Метрики имеют явные единицы: `shaft_power_total_w` (W), `feed_mass_kg_s` (kg/s),
`water_handoff_mass_kg_s` (kg/s), `water_letdown_power_w` (W),
`separator:<name>:<phase>_m3_s` (m3/s), `pressure:<node>` (Pa),
`shaft_power:<pump>` (W), `pump_head:<pump>` (m), `efficiency:<pump>` (1),
`npsh_margin:<pump>` (m), `product:<phase>:mass_kg_s` (kg/s).

В примере вход 2.994 кг/с, отделённая вода 2 кг/с, мощность насоса 392.266 Вт;
массовые невязки компонентов равны нулю в сохранённом результате. При нарушении
ограничений CLI сохраняет отчёт с `feasible: false` и возвращает код 3. Ошибки
конфигурации или физически недопустимый режим возвращают код 2, без успешного
результата. Сохранённый результат задаёт начальное приближение водяной сети;
это не перезапуск динамических запасов сепаратора.

### Газовый тракт: сухой идеальный газ и компрессия

Газовый тракт задаётся необязательным `gas_export` в конфигурации площадки.
Пример — `configs/surface_gas_facility.json`:

```bash
python scripts/run_surface_facility.py configs/surface_gas_facility.json --output /tmp/gas_facility.json
```

Реализованы десять связанных возможностей: идеальный газ с калорическими
свойствами; компрессор; охладитель; многоступенчатая цепочка; выбор числа ступеней
по ограничениям; смешение; сброс давления; сжимаемая экспортная труба;
приведение газа сепараторов к общему коллектору; общие ограничения и отчёт площадки.
Это стационарный тракт с **заданными расходами**, не расчёт произвольной газовой
сети и не совместное определение дебита скважин по давлению газосбора.

`IdealGas` задаётся удельной газовой постоянной R (J/(kg K)), отношением
теплоёмкостей k > 1 и динамической вязкостью (Pa s). Плотность ρ=p/(RT),
cp=kR/(k−1). Все давления абсолютные, температуры — K, массовые расходы — kg/s.
В пределах одной цепочки используются один газ, постоянные cp, k и вязкость;
смешение разных составов, real-gas Z, конденсация и фазовая диаграмма отсутствуют.

`GasCompressor` принимает выходное давление, `isentropic_efficiency` (0.75),
`mechanical_efficiency` (0.95), предел степени сжатия (4), температуры выхода
(500 K) и необязательные `max_drive_power_w`/`max_inlet_volume_m3_s`.
T_out = T_in·[1 + ((p_out/p_in)^((k−1)/k)−1)/η_is]. Связь основана на
[изоэнтропических соотношениях идеального газа NASA](https://www.grc.nasa.gov/www/k-12/airplane/isentrop.html)
с заданным изоэнтропическим КПД. Уменьшение давления компрессором запрещено.
Пределы расхода, температуры и мощности проверяются до выдачи результата.
Помпаж, запирание проточной части, характеристики по приведённым расходам/оборотам
и антипомпажная рециркуляция пока не моделируются.

Различаются три мощности: `gas_power_w` = m·cp·ΔT, переданная газу;
`shaft_power_w` = gas_power/η_mechanical, требуемая на валу;
`drive_power_w` — та же механическая нагрузка внешнего привода (без отдельной
модели электрического КПД двигателя). `drive_loss_w` — механические потери,
не добавляемые к энтальпии газа. Это не расчёт электрического потребления.
Проверяются баланс энтальпии газа и баланс мощности привода отдельно.

`GasCooler` задаёт выходную температуру, потерю давления как долю входного
(0 ≤ loss < 1) и необязательный предел тепловой нагрузки. Тепло Q=m·cp·(T_in−T_out)
выдаётся как положительная `rejected_heat_w`; нагрев охладителем запрещён.
Это заданный режим отвода тепла, без UA, температуры охлаждающей среды,
конструкции аппарата, конденсата и мощности вентиляторов/насосов охлаждения.

`GasTrain` последовательно соединяет оборудование и возвращает состояния всех
портов, мощности, тепло и невязки. `intercooled_train` выбирает число ступеней
и равные степени сжатия с учётом потерь **каждого** охладителя. Если предел
температуры требует больше ступеней, число увеличивается до `max_stages`;
невозможность выполнить ограничения — ошибка. Это выбор среди равноотношенных
схем, не оптимизация капитальных затрат или произвольных карт машин.
Охлаждение не нагревает уже более холодный газ. Если требуется уменьшение
давления, применяется `GasLetdown`, при одинаковом давлении — байпас.

`GasLetdown` — идеальный изоэнтальпийный сброс заданного расхода: для идеального
газа температура не меняется. Это не модель пропускной способности газового
дросселя, критического истечения или эффекта Джоуля–Томсона реального газа.
`mix_gas_streams` требует одинаковые давления портов и сохраняет массу/энтальпию;
температура смеси взвешивается по массе для общей постоянной cp. Перед смешением
каждый источник должен пройти компрессию либо сброс. У нулевой суммарной подачи
температура смеси не назначается произвольно.

### Изотермическая газовая экспортная труба

`IsothermalGasPipe(name, length_m, diameter_m, roughness_m=0)` — одна горизонтальная
труба постоянного сечения с заданными положительными направлением и расходом.
Используется уравнение импульса с изменением плотности и ускорением:

```text
p_in² − p_out² − 2·G²RT·ln(p_in/p_out) = f_D·L/D·G²RT,
G = mass_rate / area.
```

f_D — коэффициент **Darcy**, не Fanning. При постоянных температуре, вязкости,
сечении и массовом расходе Re постоянен вдоль трубы. Используются 64/Re в
ламинарной области, неявное уравнение Colebrook в турбулентной, гладкое смешение
при Re=2000–4000. Сохраняется только дозвуковая ветвь изотермического уравнения;
заданный расход, требующий достижения критической точки, отклоняется.
Критическая скорость этой модели sqrt(RT), то есть акустическое число Маха
1/sqrt(k), а не 1. Возвращаются оба числа: `outlet_mach` (акустическое) и
`outlet_isothermal_mach`, а также абсолютная/относительная невязки импульса.

Логарифмический член не отбрасывается. Результат проверен независимым
интегрированием дифференциального уравнения импульса через `solve_ivp`.
В `heat_added_w` записывается внешний подвод тепла, необходимый при принятой
изотермии для увеличения кинетической энергии потока. Температура стенки,
коэффициент теплообмена и реализуемость такого теплового режима не вычисляются.
Высотные перепады, отложения, газожидкостные пробки и нестационарный запас газа
в трубе не моделируются. Это не Fanno-модель адиабатического течения.

### Сбор газа от ступеней сепарации

`GasExportSystem` использует `header_pressure_pa`, `inlet_temperature_k` (300),
`cooling_temperature_k` (300), `standard_pressure_pa` (100000),
`standard_temperature_k` (300), `heat_capacity_ratio` (1.3), `viscosity_pa_s`
(1e-5), КПД компрессоров, `max_stage_pressure_ratio` (4),
`cooler_pressure_loss_fraction` (0.02), `max_discharge_temperature_k` (500),
`max_stages` (20), необязательный объект `export_pipe`.
R определяется по стандартной плотности газа и заданным стандартным условиям.
Плотность фазы газа **каждого** сепаратора сверяется с идеальным газом в исходном
порту с относительным допуском 1e-6. Несогласованность — явная ошибка с требованием
real-gas модели; произвольный Z вместо EOS не подставляется. Проверка в портах
не доказывает применимость идеального газа в промежуточных условиях: это
предположение всей модели и ограничение области её использования.

Газовый выход каждого сепаратора должен содержать только газовый компонент:
унос жидкости и Rv не допускаются. Каждый поток приводится к давлению коллектора
своей цепочкой, затем смешивается и проходит экспортную трубу. Газ, остающийся
растворённым в конечном нефтяном продукте, не отправляется в газовый экспорт второй раз.
Расходы определены сепарацией; давление коллектора не регулирует добычу пласта.

Добавлены метрики `gas_drive_power_w` (W, механический привод компрессоров),
`gas_cooling_duty_w` (W, только охлаждение газа), `gas_export_mass_kg_s` (kg/s),
`gas_export_pressure_pa` (Pa), `gas_export_temperature_k` (K),
`facility_drive_power_total_w` (W, сумма валовой мощности водяных насосов и
механической нагрузки газовых приводов). Старый `shaft_power_total_w` остаётся
суммой только водяных насосов. Вентиляторы, электродвигатели и вспомогательные
потребители не включены. Эти метрики доступны обычным `FacilityLimit` и не
считаются успешно проверенными при отсутствии значения. При нулевой подаче газа
коллектор и выход имеют значение null; ограничения давления на отсутствующий
поток требуют явного изменения конфигурации.

Пример содержит синтетические PVT, согласованные с сухим идеальным газом при
300 K; не является калибровкой на Norne или промышленной газовой смеси.
Проверяются баланс массы экспорта, баланс энергии каждой цепочки и всей газовой
части, повторный расчёт из сохранённого результата и нарушения ограничений.

### Управление подачей и ограничение производительности площадки

`SurfaceFacility.run()` принимает `feed_scales`, `pump_speed_ratios`,
`valve_openings`, `gas_header_pressure_pa`, `gas_cooling_temperature_k`.
`feed_scales` — упорядоченные доли доступной подачи каждого входного потока,
от 0 до 1; состав каждого потока сохраняется. Без аргумента доли равны 1.
Параметры оборудования переопределяются только для вызова, исходная установка
и потоки не меняются. Управления возвращаются в `operating_controls`.
Это внешнее ограничение доступной подачи на установку, не перерасчёт дебитов
скважин по индикаторным кривым и не обратная связь с FIM пласта.

`FacilityCapacityControl` ищет допустимую долю общей подачи, сохраняя соотношение
между запрошенными входными потоками. Поля: `min_fraction` (0.05),
`max_fraction` (1), `fraction_tolerance` (1e-5), `scan_points` (17),
`max_evaluations` (80). Требуются 0 < min < max ≤ 1 и бюджет не меньше размера
сканирования. Нижняя граница положительна: нулевая подача воды не задаёт рабочую
точку гидравлической модели; для остановки есть отдельное состояние расписания.

Сначала проверяется максимальная разрешённая подача. Если она недопустима,
сканируется диапазон, затем уточняется граница над наибольшей найденной допустимой
точкой. Результат всегда остаётся с **допустимой** стороны границы; ограничения
не ослабляются на численный допуск. Нельзя считать этот метод глобальным
оптимизатором произвольной установки. Требуется одна связная допустимая область;
обнаруженные при сканировании разрывы отклоняются. Узкая область между узлами
сетки может быть пропущена: отсутствие допустимых проб не доказывает глобальную
невозможность режима. Для независимого распределения подач между скважинами
и несвязных областей нужен другой оптимизатор.

Статусы: `requested` (полная запрошенная подача), `max_allowed` (достигнут
заданный max_fraction < 1), `limited` (найдена граница ограничений),
`no_feasible_sample` (допустимая точка на пробах не найдена; facility = null).
Выдаются принятая доля, недопустимая верхняя граница, принятые доли потоков,
непроизведённая потенциальная подача компонентов, журнал проб и ограничения,
нарушенные у верхней границы. `evaluations` считает проверенные доли подачи;
`cold_retry` отдельно отмечает повторный расчёт без начального приближения.
Исчерпание бюджета — ошибка, а не успешное приближение неизвестной точности.

Численная несходимость не считается пределом мощности. После неудачи с тёплым
стартом допускается одна попытка с холодным; повторная ошибка передаётся наружу.
`PropertyModelError` (например, несовместимость PVT и идеального газа) не скрывается
за снижением подачи. `ConservationError` относится к численным ошибкам, а не
к допустимой перегрузке оборудования. Параметры за областью оборудования могут
отклонять отдельные пробы с явно сохранённой причиной.

```bash
python scripts/run_surface_facility.py configs/surface_capacity_limited_facility.json --capacity-control configs/surface_capacity_control.json --output /tmp/dispatch.json
```

В примере суммарная механическая мощность ограничена 20 кВт. Принятая подача
около 0.61442 исходной, мощность около 19999.77 Вт. Результат содержит обычный
расчёт в `facility`; его можно использовать через `--initial-state`.
Отсутствие допустимой пробы возвращает код 3 и сохраняет отчёт. Численные ошибки
и ошибки конфигурации возвращают код 2. Непроизведённый потенциал подачи не
считается сбросом/факелом и не добавляется к материальному балансу установки.

### Расписание установившихся режимов

`FacilityPeriod` задаёт `name`, положительную `duration_s`, необязательные
`feed_scales`, `pump_speed_ratios`, `valve_openings`,
`gas_header_pressure_pa`, `gas_cooling_temperature_k`, `shutdown` (false).
Имена периодов уникальны. Значения управлений переходят в следующий период;
словари меняют только перечисленные агрегаты. Пустой словарь не сбрасывает
управления; для возврата нужно явно задать исходное значение. `shutdown` относится
только к указанному периоду и не наследуется автоматически.

`run_facility_schedule` на каждый период рассчитывает одну установившуюся
рабочую точку, при необходимости с `FacilityCapacityControl`. Допустимые расходы
умножаются на длительность: накапливаются принятые и продуктовые объёмы стандартных
компонентов, непроизведённый потенциал подачи и механическая/тепловая энергия.
Газ в конечном нефтяном продукте остаётся газовым компонентом при суммировании,
поэтому не теряется и не учитывается второй раз. Сверяется компонентный баланс
накопленных объёмов при одинаковых стандартных условиях.

Это **не** нестационарное моделирование сепаратора, заполнения газопровода,
разгона двигателя или интегрирование пласта. Время здесь — длительность удержания
установившейся точки. Переключения мгновенны; никаких скрытых запасов массы или
энергии между периодами не добавляется. Для настоящей динамики необходимы
уравнения запасов и соответствующие неизвестные.

При `shutdown: true` гидравлическая рабочая точка не назначается: facility = null,
продукция и затраты энергии равны нулю, доступный потенциал подачи записывается
как непроизведённый. Давления остановленного оборудования не копируются из
работающего режима. Предыдущий результат сети хранится только как численное
начальное приближение следующего запуска. Изолированным узлам не присваиваются
произвольные давления. Имена управляемых агрегатов проверяются и на остановке.

Энергии `shaft_power_total_j`, `gas_drive_power_j`, `gas_cooling_duty_j`,
`water_letdown_power_j` хранят соответствующие интегралы метрик мощности в Дж.
`facility_mechanical_energy_j` — сумма механических нагрузок водяных и газовых
агрегатов; она не включает электрический КПД двигателей и вспомогательное
оборудование. Тепловые нагрузки и сброс давления учитываются отдельно и не
прибавляются повторно к механическому потреблению.

### Перезапуск расписания и проверка совместимости

```bash
python scripts/run_surface_schedule.py configs/surface_capacity_limited_facility.json configs/surface_operation_schedule.json --output /tmp/schedule.json
python scripts/run_surface_schedule.py configs/surface_capacity_limited_facility.json configs/surface_operation_schedule.json --stop-after 2 --output /tmp/partial.json
python scripts/run_surface_schedule.py configs/surface_capacity_limited_facility.json configs/surface_operation_schedule.json --checkpoint /tmp/partial.json --output /tmp/resumed.json
```

`--stop-after` ограничивает число **дополнительных** периодов текущего вызова.
Чекпоинт хранит позицию, время, наследуемые управления, журнал завершённых периодов
и последнее начальное приближение сети. Контрольная сумма обнаруживает случайное
повреждение; это не криптографическая защита от намеренного изменения пользователем.
Отпечатки включают конфигурацию установки/PVT, расписание, настройки контроллера
исходный код расчётных модулей и версии Python/NumPy/SciPy. Изменённый план,
модель или вычислительное окружение отклоняются вместо
незаметного продолжения на другой физике. Даже форматирование исходных модулей
меняет этот консервативный отпечаток.

Проверяются положение продолжения, длительности, имена периодов, конечность и
неотрицательность накопленных величин и компонентный баланс. Входной чекпоинт
копируется: неудачный период не изменяет его. При нарушении ограничений без
контроллера, отсутствии допустимой пробы с контроллером или физической ошибке
период не считается завершённым. CLI не выдаёт частичный ошибочный прогон как
успешный результат. Сравнивать продолжение с непрерывным расчётом следует по
итогам и checkpoint: `processed_periods` относится только к текущему вызову.

### Физическая обратная связь FIM → скважины → трубная сеть

`simulation.physical_surface_network` включает неявную связь скважин с физическими
трубами. Первый поддерживаемый режим: `fim_model: "oil_water"`, аналитические
свойства Fluid без black-oil PVT, привязанные водяные добывающие скважины,
открытые пассивные трубы. Нефтяная подвижность в привязанных перфорациях должна
быть нулевой в пределах относительного численного допуска 1e-12. Наличие
существенной нефтяной подвижности выдаёт `PropertyModelError`, даже если текущий
нулевой перепад случайно даёт нулевой нефтяной дебит. Газ и black-oil отклоняются
явно, а не подменяются водой. Нужна ненулевая водяная продуктивность; закрытые
все перфорации этой модели связи пока не поддерживаются.

Объект содержит `network` (обычная конфигурация `LiquidNetwork`) и `well_nodes`
(имя скважины → имя узла сети). У всех узлов исходный `source_mass_rate_kg_s`
равен нулю: источники создаются расходами привязанных скважин. Привязанный узел
не может иметь заданное давление. Плотность и вязкость поверхности совпадают
с опорной плотностью воды и водяной вязкостью Fluid; сама трубная сеть остаётся
несжимаемой, изотермической и с постоянными свойствами. Это не расчёт изменения
плотности и температуры вдоль реального ствола.

Привязанные скважины имеют `type: "producer"`, `control_type: "rate"` и
`surface_phase: "water"` либо `"liquid"`. Заданный дебит становится **верхней
границей**: фактический расход определяется притоком из пласта и давлением сети.
Используется `bhp_min`, если он задан. Насосы, дроссели и обратные клапаны внутри
графа этой первой FIM-связи запрещены; VFP/MSW на той же скважине не допускаются.
Отдельные наземные расчёты этих устройств остаются доступными.

Узел привязки расположен на **опорной глубине BHP**, не на устье:
`elevation_m = -well.ref_depth` в общей системе координат. Вертикальная труба
от этого узла до наземного коллектора представляет гидростатику и трение ствола.
Гидростатика между перфорациями и опорной точкой остаётся в FIMWells, а между
опорной точкой и поверхностью — в трубах. Дополнительная VFP-поправка к этой
связи не добавляется. Нельзя указывать устьевую отметку 0 вместо глубины BHP:
проверка отметок отклонит такую конфигурацию.

На каждой итерации Ньютона сеть решается по текущим массовым подачам скважин.
`pressure_sensitivities` вычисляет dP_node/dQ_mass из неявного Якобиана сети,
без конечных разностей. Затем строятся полные межскважинные B и D:
`r_surface = p_bh − P_network(Q_all)` для открытого свободного режима.
Производная давления общего коллектора по дебиту соседней скважины входит
в линейную систему, а не обновляется отдельной запаздывающей поправкой.

Полный D исключается в FGMRES через дополнение Шура. Локальный вклад для CPR
содержит и связи разных скважин в общей перфорированной ячейке. Исключение,
восстановление поправок BHP и оператор проверены против явной полной матрицы;
производные — против конечных разностей. Текущая реализация хранит плотный
скважинный блок и поддерживает до 128 скважин и 10000 соединений. Она не
увеличивает размер пластовой BSR-матрицы; производительность больших таких
связанных моделей пока не заявляется.

Условия дополнительности обеспечивают четыре режима: `surface` (давление сети),
`rate` (верхняя граница дебита), `bhp_limit` (нижний предел BHP), `surface_stop`
(отсутствие прямого притока против давления сети). В режиме дебита/BHP лишний
перепад интерпретируется как **идеальное регулирование скважины**, а не как
дополнительно заданная характеристика реального дросселя. Его гидравлическая
диссипация возвращается в `ideal_choke_dissipation_w`. На остановке не навязывается
равенство BHP с давлением внешней сети; закрытый интерфейс удерживает перепад,
а скважина имеет нулевой результирующий расход в пределах допуска. Снижение
противодавления может снова открыть скважину без ручного смены режима.

`solver.wells.surface_report` содержит давления/потоки сети и состояние каждой
привязанной скважины. При фиксации успешного шага сохраняются `surface_mode` и
`surface_reference_pressure_mpa` на объекте скважины. Метод
`set_surface_boundary_pressures({node: pressure_pa})` меняет только существующие
узлы заданного давления, не меняя топологию и привязки.

Численный отказ трубной сети или связанного скважинного блока возвращает отказ
FIM-подшага после отката пластовых и скважинных состояний. Адаптивный `run_step`
может дробить шаг; причина доступна в `last_surface_failure`. Ошибка области
физики/PVT не скрывается дроблением шага. Отчёт поверхности при неудаче тоже
возвращается к предыдущему принятому состоянию.

Сохранённые поля давления/насыщенностей для этой связи переводятся в float64,
чтобы округление принятого слоя не разрушало проверенный баланс.
CNV, MB и скважинные критерии не ослабляются ради сходимости поверхности.

Воспроизводимый малый пример с двумя скважинами и общим коллектором:

```bash
python scripts/run_fim_surface.py configs/fim_water_surface.json --outlet-mpa 6 8 10 12 --days 1 --output /tmp/fim_surface.json
```

Скрипт запускает CPU-расчёты через `Simulator.run_step` из одинакового начального
состояния для каждого давления. Сохраняются принятые подшаги, давления, режимы,
итеры Ньютона и баланс массы всего пласта с учётом всех скважинных источников.
В синтетическом примере за сутки получено около 44.07, 26.25, 3.08 и 0 м³ воды
соответственно. Последний ноль имеет обычную машинную погрешность (менее 1e-8 кг
за сутки), которая остаётся в отчёте, а не обрезается для улучшения баланса.
Это проверка связи и переключений, не эталон Norne и не сравнение с Eclipse.

Сохранённый контрольный прогон: `results/fim_physical_surface_20261031/pressure_sweep.json`.
В `validation.json` рядом записаны баланс каждого случая, результаты проверок
и SHA-256 исходников. Общий регрессионный набор: 160 пройденных проверок;
последний отдельный запуск новой связи: 8 пройденных проверок.

Для нефти/газа ещё требуются многофазная гидравлика ствола/шлейфов и согласованные
производные PVT/удержания фаз. Отдельные сквозные примеры сепарации/компрессии
пока не становятся автоматически частью этой монолитной FIM-связи.

### Многофазная труба с однородной скоростью фаз

`src/surface/multiphase.py` — отдельная модель `HomogeneousPipe`. Она пока
**не подключена к FIM/Norne**. Это стационарная изотермическая труба постоянного
сечения с фиксированными массовыми долями несмешивающихся нефти, воды и свободного
идеального газа. Плотности жидкостей постоянны. Все фазы движутся с одинаковой
скоростью: проскальзывание, смена режимов течения и эмульсионная реология не
моделируются. Такой смысл однородного приближения описан, например, в
[документации TrioCFD](https://triocfd-documentation.readthedocs.io/v1.9.8/MP_HEM.html).
Наша модель имеет фиксированный состав и не выполняет равновесный flash.

Для массовых долей `x_i` удельный объём смеси:
`v(p) = x_o/rho_o + x_w/rho_w + x_g R T/p`.
Динамическая вязкость усредняется по локальным объёмным долям — это явное
замыкание модели, а не универсальная корреляция для нефтяных эмульсий.
Массовый поток на единицу площади `G` постоянен. Интегрируется уравнение:

```text
(1 − G² x_g R T / p²) dp/ds = −f_D G² v/(2D) − (g/v) dz/ds
```

Трение: ламинарное `64/Re`, турбулентное Colebrook, плавный переход 2000–4000.
Ускорение расширяющейся смеси входит в знаменатель уравнения. Интегратор
останавливается до критического режима либо минимального допустимого давления;
за пределами области выдаётся ошибка, продолжение сверхкритической ветви не
подставляется. Отрицательные расходы и нулевой суммарный расход отклоняются:
статическое распределение фаз требует отдельного описания удержания фаз.

Отчёт содержит расходы фаз, долю газа на входе/выходе, скорости, запас до
критического режима и аудит механической энергии:
`m [integral(v dp) + delta(u²/2) + g delta(z) + integral(f_D G² v²/(2D) ds)]`.
Это не тепловой баланс и не расчёт температуры. Газ здесь именно свободный;
подавать вместо него поверхностный газ вместе с растворённым нельзя.

```bash
python scripts/run_surface_multiphase.py configs/surface_homogeneous_pipe.json --output /tmp/multiphase_pipe.json
```

В примере: 1 кг/с нефти, 1 кг/с воды и 0.1 кг/с газа; труба 1200 м, диаметр
0.08 м, подъём 300 м, температура 320 K. При входе 8 МПа выход составляет
около 6.52125 МПа. Этот результат проверяет выбранное замыкание, но не заменяет
валидацию по экспериментам и многофазным промышленным корреляциям.

До связи с black-oil FIM остаются: согласованное выделение свободных фаз из PVT,
производные по давлениям и компонентным расходам, сборка узлов смешения,
модель проскальзывания/удержания фаз и проверки полного связанного Якобиана.

### Сквозная black-oil сеть сбора и наземная установка

Новый пример `configs/surface_gathering_facility.json` связывает:

```text
притоки A/B → многофазные шлейфы → общий коллектор
→ первая ступень сепарации → последующие ступени
→ водяная сеть / компримирование и экспорт сухого газа
```

Этот пример использует **заданные компонентные притоки**. Отдельный пример
`configs/fim_blackoil_surface.json` добавляет ограниченную неявную обратную связь
с black-oil FIM; её условия приведены ниже.
Наземный эталон работает на CPU в float64. Для связанного FIM добавлены
CUDA-пласт/Шур и опциональные CUDA-ядра PVT/квадратуры/AD сети. Обход дерева и
скалярное управление поиском давления остаются на CPU. Согласие с промысловыми
измерениями и скорость на больших полевых моделях пока не заявляются.

#### Свойства и выделение газа

`BlackOilMixture` принимает существующий `PVTTable` либо словарь PVT и
`StockDensities`. Внешние давления — Па, компонентные массы — кг/с. Таблицы
используют `pressure_MPa`, `Bo/Bw/Bg`, `mu_*_cP`, `Rs_m3m3`, `Rv_m3m3`, как
остальной проект. Вязкость переводится из cP в Па·с. Плотности — при стандартных
условиях. Газовая компонентная масса включает растворённый газ.

При стандартных объёмных эквивалентах `qo`, `qw`, `qg`:

```text
Rs_actual = min(Rs_sat(p), qg/qo)
Q_oil = qo Bo(p, Rs_actual)
Q_water = qw Bw(p)
Q_free_gas = (qg − qo Rs_actual) Bg(p)
m_oil_phase = m_oil_component + rho_gas_sc qo Rs_actual
m_gas_phase = m_gas_component − rho_gas_sc qo Rs_actual
```

Газ переносится между нефтяной и газовой фазами без изменения компонентных
масс. При смешении притоков сначала складываются компоненты, после чего фазы
пересчитываются при местном давлении. Складывать объёмы свободного газа из
разных давлений вместо этого нельзя.
При чистой воде запрос производных по трём компонентам требует PVTO для
нулевого газосодержания: без него неизвестен эффект добавления нефти, и такой
Якобиан явно отклоняется. Само водяное состояние без этих производных доступно.

Поддержан растворённый газ `Rs`, но не испарённая нефть `Rv`.
Для недонасыщенной нефти обязательны реальные расширенные таблицы PVTO,
покрывающие состав потока и весь диапазон давления наземной модели.
Проверяется непрерывность `Bo` и вязкости на давлении насыщения данного состава.
Несогласованные таблицы отклоняются; значения не подправляются для прохождения
проверки. Давления вне таблиц, отрицательные расходы и нулевой общий расход
тоже отклоняются. Для очень широких пластовых PVT рекомендуется подготовить
проверенный диапазон поверхности, а не рассчитывать на экстраполяцию.

#### Труба и производные

`BlackOilPipe` использует равные скорости фаз и объёмное усреднение динамической
вязкости. Это однородное приближение: отдельные скорости/удержание фаз,
эмульсионные свойства, пробковый режим, теплообмен и температурный flash пока
не моделируются. PVT считается заданной изотермой. Трубы постоянного сечения;
направление — горизонтально либо вверх. Нисходящие участки явно отклоняются.

Для `v = (Q_oil + Q_water + Q_free_gas) / m_total`:

```text
(1 + G² dv/dp) dp/ds = −f_D G² v/(2D) − (g/v) dz/ds
```

`BlackOilPipe.run` находит выходное давление по входному;
`required_inlet` решает обратную задачу по заданному давлению приёмника.
Интеграл длины считается в координате давления квадратурами Гаусса с контролем
точности. Интервалы разбиваются на узлах PVT и на **зависящем от состава**
давлении появления газа. Ламинарное/переходное/турбулентное трение согласовано
с объявленной моделью Colebrook. Неактивная турбулентная ветвь не вычисляется
на недопустимых малых Re.

Производные по граничному давлению и трём компонентным массовым расходам
получаются через autograd и теорему о неявной функции. В них входит перемещение
границы насыщения при изменении состава. Конечные разности используются для
проверки, а не для производных рабочего решателя. На изломах таблиц и границах
активных фаз производная кусочная; центральная разность в самой точке излома
не обязана совпадать с одной из односторонних производных.

Отчёт содержит состояния фаз на обоих портах, производные, невязку длины,
контроль квадратуры, запас `1 + G² dv/dp`, трение и баланс механической энергии.
Отклонение последнего вызывает отказ, а не только записывается в лог.
Это не тепловой баланс: потребное тепло для поддержания изотермы не вычисляется.

Ошибки различаются:

- `ChokedFlowError` — известная физическая граница пропускной способности;
- `PropertyModelError` — неподдержанная физика, состав или диапазон PVT;
- `HydraulicConvergenceError` — численный отказ квадратуры/инверсии;
- `ConservationError` — нарушенный баланс.

Диспетчер может уменьшать расход из-за физического запирания, но не маскирует
плохую PVT или численный отказ как обычное превышение мощности установки.

#### Дерево сбора и общий коллектор

`BlackOilProductionNetwork` принимает узлы `ProductionNode` и трубы
`ProductionPipe`. Геометрическая высота трубы вычисляется из высот узлов;
отдельная гидростатическая поправка поверх этого не добавляется.

Допускаются слияния потоков и один приёмник с заданным абсолютным давлением.
Разделение потока, кольца, реверс, несколько приёмников и нулевой расход в
отдельной ветви пока не поддержаны. При нуле нужен самостоятельный физический
выбор статического заполнения, который эта модель не угадывает.
Все притоки используют одну PVT-модель и одну изотерму.

Давления восстанавливаются от приёмника к источникам после компонентного
суммирования снизу по дереву. `pressure_derivatives_per_kg_s` содержит полную
связь давления каждого узла с компонентными расходами каждого источника.
Сопротивление общего коллектора поэтому входит в производную давления A по
дебиту B и наоборот. `pressure_derivatives_receiving_pressure` содержит
производные по давлению приёмника. Эти производные проверены конечными
разностями, включая изменение состава соседнего притока.

#### Передача в технологическую установку

`GatheringFacility` соединяет сеть с существующей `SurfaceFacility`.
Обязательны одинаковые стандартные плотности, PVT и давление приёмника,
равное давлению первого сепаратора. Передача проверяется и по компонентным
массам, и по объёмам фаз при этом давлении. Далее работают существующие
водяные насосы/клапаны и модель сухого газа с её собственными ограничениями.

Дополнительные метрики:
`gathering_pressure:<node>` (Па) и `gathering_friction_dissipation_w` (Вт).
Для них доступны обычные `FacilityLimit` и равномерное ограничение притоков
через `FacilityCapacityControl`. Это ограничение заданного притока, не
согласование с пластовой индикаторной кривой и не автоматическая настройка
реальных скважинных дросселей.

```bash
python scripts/run_surface_gathering.py configs/surface_gathering_facility.json --output /tmp/gathering.json
python scripts/run_surface_gathering.py configs/surface_gathering_facility.json --max-pressure A 1300000 --capacity-control configs/surface_capacity_control.json --output /tmp/gathering_limited.json
python scripts/run_surface_schedule.py configs/surface_gathering_facility.json configs/surface_gathering_schedule.json --gathering --output /tmp/gathering_schedule.json
```

Пример даёт около 1.395 МПа на входе A, 1.260 МПа на входе B и 1.182 МПа в
коллекторе при приёмнике 1 МПа. Это результаты синтетической конфигурации,
а не эталон Eclipse. При добавлении ограничения A до 1.3 МПа диспетчер находит
меньший допустимый положительный приток.

Расписание поддерживает полную остановку установки без вымышленных давлений
в остановленных трубах. После возобновления выполняется новый стационарный
расчёт. Полный запуск и продолжение из чекпоинта проверяются на точное равенство.
Проверка совместимости чекпоинта включает геометрию дерева, привязки притоков,
PVT/вязкости, ограничения и реализацию моделей; изменения требуют нового
расчёта. Энергия трения сети накапливается отдельно от механической энергии
приводов, чтобы не считать диссипацию дополнительной мощностью компрессоров.

#### Независимая численная проверка

```bash
python scripts/check_surface_blackoil.py --cases 32 --output /tmp/blackoil_check.json
```

Этот скрипт сравнивает рабочую квадратуру по давлению с отдельным пространственным
ODE-интегратором. Эталон самостоятельно интерполирует PVT в NumPy и решает
Colebrook через `scipy.brentq`; рабочий flash и его квадратуру он не вызывает.
Пространственный эталон явно локализует события пересечения узлов PVT и
давления насыщения, после чего продолжает на следующей гладкой ветви.
Без такого события ODE-интегратор может пропустить скачок производной даже
при малом относительном допуске; соответствующий случай сохранён в
`tests/data/surface/blackoil_phase_transition.json`.
Дополнительно проверяются обратная задача и компонентный Якобиан. Фиксированный
seed обеспечивает воспроизводимость параметров. Сверка подтверждает численное
решение выбранных уравнений, но не подтверждает применимость однородного
приближения к любому многофазному промысловому течению.

Сохранённый пакет: `results/surface_gathering_20261031/validation.json`.
В численной сверке 16384 режимов, включая 503 случая появления газа внутри
трубы: максимальное расхождение с отдельным пространственным решением около
2.6e-6 Па. На 2048 режимах дополнительно проверены компонентные производные;
максимальная нормированная ошибка около 1.22e-6. Основной регрессионный набор —
205 пройденных проверок; отдельно сохранены проверки граничных составов и
фазового перехода в общей сети. Это точность численного решения выбранного
приближения, а не оценка ошибки относительно реального многофазного потока.

### Неявная связь black-oil FIM с физическим деревом сбора

Пример `configs/fim_blackoil_surface.json` включает `physical_surface_network`
с `network.model: "homogeneous_blackoil_tree"` и привязками `well_nodes`.
Это обратная связь внутри Ньютона, а не внешний пересчёт уже заданных дебитов:
дебиты зависят от ячеек и BHP, а давления сети — от компонентных дебитов всех
скважин. Сквозные прогоны выполняются через `Simulator.run_step` на CPU или CUDA.

Область поддержки этого первого подключения намеренно ограничена:

- одна общая явная `PVTTable`, одинаковые стандартные плотности и PVTO;
- все скважины — активные добывающие, все привязаны к сети;
- положительные верхние уставки стандартного дебита нефти/воды/газа/жидкости;
- положительная добыча без перетоков в перфорациях и нулевых ветвей;
- перфорации на отметке BHP: вертикальная часть подъёма моделируется сетью;
- WEFAC=1; VFP, MSW, группы, газлифт и неоднородные PVT-регионы не совмещаются;
- CPU или CUDA для пласта, скважинных блоков и Шура; вариант вычисления сети
  задаётся отдельно, как описано ниже.

Ограничения проверяются, а неподдержанная физика не заменяется фиктивным расходом.
На нулевом расходе требуется самостоятельная модель заполнения ствола/труб;
пока нет её корректного выбора, считать такой режим этим подключением нельзя.
Обычный black-oil FIM без `physical_surface_network`, включая VFP/Norne,
продолжает использовать существующий путь.

Связанные режимы: `surface` (давление сети), `rate` (верхний предел дебита),
`bhp_limit` (нижний предел BHP). Лишний перепад на режиме дебита/BHP соответствует
идеальному регулированию, а не заданной характеристике физического дросселя.
Масштаб проекции для выбора активной строки привязан к текущему расходу;
увеличение неактивного верхнего лимита само по себе не должно толкать начальный
Ньютон к недостижимому большому расходу. Критерии CNV/MB/BHP не ослабляются.

Полная связь входит в скважинные блоки `B_full` и `D_full`, включая влияние
соседней скважины через коллектор. Общий `FullWellSchur` исключает плотный
скважинный блок для пластовых блоков 2×2 или 3×3; локальная часть для CPR
собирается по уникальным перфорированным ячейкам. Полный оператор, правая часть
и восстановление BHP проверяются против явной полной матрицы. Допустимы до
128 скважин и 10000 соединений; производительность больших связанных полевых
моделей пока не измерена.

`solver.wells.surface_report` содержит давления сети, режимы, BHP,
`component_mass_rates_kg_s` (порядок нефть/вода/газ) и
`standard_control_rate_m3_s` каждой скважины. Метод
`set_surface_boundary_pressures({receiver: pressure_pa})` меняет давление
существующего приёмника. Произвольное изменение топологии этим методом запрещено.
Численный отказ возвращает отказ FIM-подшага после отката полей, Rs/фазового
состояния, скважин и отчёта поверхности. `Simulator` может дробить шаг;
`last_surface_failure` содержит причину гидравлического отказа.

В JSON-ветке `BlackOilPVT` исправлено использование расширенной PVTO:
если таблицы заданы, недонасыщенные `Bo`/вязкость берутся из них, с интерполяцией
по давлению и Rs, вместо прежнего экспоненциального приближения. Производные
работают через `torch.func.jvp`. При отсутствии расширенной PVTO старое
приближение обычного FIM сохраняется, но физическая поверхность требует
полного покрытия своей области свойств. Проверено равенство недонасыщенных
свойств пласта и поверхности и их производных; насыщенные и недонасыщенные
связанные интервалы проверены по балансам всех компонентов.

Квадратура трубы при недостаточной точности порядка 256 теперь делит интервал
давления с распределением абсолютного допуска между половинами. Это нужно
около переходов трения по Re. Порог ошибки не увеличивается, а производные
остаются частью дифференцируемого интеграла.

```bash
python scripts/run_fim_blackoil_surface.py configs/fim_blackoil_surface.json --outlet-mpa 0.8 1 1.2 --days 1 --output /tmp/fim_blackoil_surface.json
python scripts/run_fim_blackoil_surface.py configs/fim_blackoil_surface.json --outlet-mpa 1 --days 10 --report-days 0.5 --output /tmp/fim_blackoil_10days.json
```

Каждый вариант давления начинается из одинакового состояния. Отчёт сохраняет
принятые подшаги, интегральный отбор каждого компонента, общий компонентный
баланс, состояния фаз и давления/режимы сети. Многосуточный расчёт проходит
последовательные отчётные интервалы заданной длины; это позволяет отдельно
сравнивать ошибку по времени. Проверка с шагами 1, 0.5 и 0.25 суток показывает
сходимость накопленной добычи при измельчении шага, а не равенство результатов
для разных дискретизаций. Это синтетический пример новой связи, не Norne
и не сравнение с Eclipse.

Контрольный пакет этого подключения:
`results/fim_blackoil_gathering_20261031/validation.json`.
Регрессионный набор: 244 проверки прошли, 11 пропущены по условиям среды.
Тридцатисуточный синтетический пример прошёл 60 последовательных интервалов;
максимальная абсолютная ошибка компонентного баланса за весь расчёт — около
4.1e-4 кг. Дополнительно сохранены суточные опыты с противодавлением
0.8/1/1.2 МПа и десятисуточные расчёты с шагами 1/0.5/0.25/0.125 суток.
Разности накопленной добычи между последовательными измельчениями шага
уменьшаются примерно вдвое, как ожидается для первого порядка по времени.
Это не оценка погрешности относительно промысловых данных.

После добавления дробления квадратуры отдельно проверены 4096 режимов при
входных давлениях 0.8–1.2 МПа, включая переходы через узел PVT 1 МПа:
расхождение с независимым пространственным решением не превысило 0.00018 Па;
на 512 режимах дополнительно проверены компонентные производные.
Расширенная PVTO в пластовом решателе хранится на объединении узлов давления
с табличными значениями по Rs; вычисление использует четыре соседних значения
на ячейку и не создаёт промежуточную матрицу «все Rs × все ячейки».

### GPU-исполнение связанного пласта и поверхности

`--device cuda` в `scripts/run_fim_blackoil_surface.py` размещает пластовые
поля, Якобиан, скважинные блоки B/D и исключение Шура на CUDA. CUDA-граф свойств
пласта остаётся активным; неявная поверхность выполняется вне его записи.
При отсутствии доступного CUDA-устройства команда завершается ошибкой;
неявной подмены GPU-расчёта CPU-расчётом нет.

Для `physical_surface_network` black-oil модели добавлен `network_backend`:

- `cpu_reference` — по умолчанию. Эталонная квадратура/PVT/AD сети на CPU,
  пласт и линейный решатель на выбранном устройстве. Из GPU передаются только
  малые массивы компонентных дебитов и BHP; межскважинные производные загружаются
  одним массивом, а B/D собираются векторно на GPU.
- `torch_device` — PVT, квадратура трения/гидростатики/ускорения и её
  autograd-производные выполняются на устройстве пласта. При `--device cuda`
  таблицы PVT и узлы квадратуры находятся на GPU; при `--device cpu` это CPU.
  Режим не означает полностью записанный CUDA-граф всей сети: обход дерева,
  скалярный поиск давления и управление адаптивными интервалами остаются на CPU.
  Промежуточные отчёты и малый перенос производных по дереву также обрабатываются
  на хосте. Пакетный поиск для многих ветвей — следующий этап оптимизации.

Уравнения, FP64, допуски и активные ограничения одинаковы для обоих вариантов.
`BlackOilMixture.to(device)` создаёт отдельный снимок таблиц на устройстве,
не меняя исходный эталон. `surface_report.execution` содержит фактические
устройства и backend; отчёт каждой трубы содержит `compute_device`.

Перед запуском явно выберите разрешённую карту через `CUDA_VISIBLE_DEVICES`.
Для повторяемых CUDA-операций можно задать `CUBLAS_WORKSPACE_CONFIG=:4096:8`.

```bash
python scripts/run_fim_blackoil_surface.py configs/fim_blackoil_surface.json --device cuda --network-backend cpu_reference --outlet-mpa 1 --output /tmp/fim_cuda_hybrid.json
python scripts/run_fim_blackoil_surface.py configs/fim_blackoil_surface.json --device cuda --network-backend torch_device --outlet-mpa 1 --output /tmp/fim_cuda_quadrature.json
python scripts/benchmark_fim_surface_gpu.py --size 256 --days 3 --repeats 3 --output /tmp/fim_gpu_benchmark.json
```

Бенчмарк создаёт одинаковую синтетическую замкнутую модель с двумя скважинами
в противоположных углах сетки. Перед каждым backend выполняется один
неизмеряемый интервал прогрева. Затем каждый повтор начинает новую модель;
первый измеренный интервал включает запись нового CUDA-графа. Отдельно
сохраняются общее время, время первого интервала и медиана последующих.
Проверяются поля, накопленный отбор компонентов и сохранение CUDA-графов.
Размер сетки и все параметры записываются в JSON. Это не бенчмарк Norne.

Пакет проверки CUDA: `results/fim_surface_cuda_3090_20261031/validation.json`.
На RTX 3090 для синтетической сетки 256×256×1 с двумя скважинами, после
одинакового прогрева и трёх повторов, медиана времени последующего отчётного
интервала составила около 0.686 с на CPU, 0.234 с для CUDA-пласта с CPU-сетью
и 0.497 с при CUDA-квадратуре/AD сети. Гибрид дал ускорение около 2.93× по
этой метрике (около 2.85× по полному времени трёх интервалов). Поэтому сеть
`cpu_reference` оставлена по умолчанию. Эти результаты не переносятся
автоматически на Norne, другую геометрию или число скважин.

Максимальная разница итогового давления CPU/CUDA в бенчмарке — около 1.9e-9 Па.
Оба варианта CUDA также прошли 30 суток по 60 интервалам с сохранением графа
свойств и компонентных балансов. CUDA-набор содержит 13 пройденных проверок,
включая режимы дебита/BHP, насыщенные и недонасыщенные ячейки и откат.
CPU-набор: 244 прошли, 24 пропущены по окружению (включая CUDA-проверки при
скрытых устройствах). Пакет сохраняет UUID использованной карты, параметры,
поля, замеры, логи и контрольные суммы исходников.

Дополнительное сокращение обменов (31.10.2026): статусы допуска и массивы
скважин передаются одним D2H-пакетом, ответ сети — одним асинхронным H2D-пакетом
через pinned memory. Геометрические индексы переиспользуются. Проверки
сходимости и отчёты скважин читают агрегированные пакеты; FP64, допуски,
порядок суммирования по перфорациям и накопленные объёмы сохранены.
Это не полностью GPU-resident исполнение: CPU управляет шагами и поиском
давления сети. Профиль отдельных участков воспроизводится командой
`python scripts/profile_fim_surface_transfers.py --output /tmp/fim_transfers.json`.
Артефакты проверки: `results/fim_gpu_transfer_optimization_20261031/validation.json`.

## Активная водяная сеть и насосная станция

Рабочие примеры: `configs/fim_water_surface_active.json`,
`configs/surface_station_facility.json`, `configs/surface_station_schedule.json`.
В спецификации водяной связи FIM допустимы `network`, `well_nodes`, `controls`,
`pressure_control`. В `controls`: карты `pump_speed_ratios`, `pump_status`,
`valve_openings`. Смена граничного давления сохраняет насосы и арматуру.

Регулятор `pressure_control`: `pump`, `node`, `target_pressure_pa`,
`min_speed_ratio`, `max_speed_ratio`, `pressure_tolerance_pa`, `max_evaluations`,
`method` (`bisect` или `newton`), `response_direction` (`increasing`, `decreasing`,
`auto`), `linked_pumps` (дополнительные насосы на общей скорости).
FIM по умолчанию использует safeguarded Newton, автоматическое направление
и допуск давления 1e-4 Па. Предел скорости — допустимый режим с фактическим
давлением; нарушение физического ограничения оборудования — ошибка и откат.

В конфигурации площадки необязательный `pump_station_control` содержит:
`pumps` (1–8 параллельных насосов с обратными клапанами), `node`,
`target_pressure_pa`, `min_speed_ratio`, `max_speed_ratio`, `min_running`,
`max_running`, `max_station_power_w`, `min_npsh_margin_m`, `min_pump_flow_m3_s`,
`switch_saving_w`, `pressure_tolerance_pa`, `scan_points`, `max_configurations`,
`max_control_evaluations`, `response_direction`. Выбор состава ограничен бюджетом
перебора и сканированием допустимых скоростей; глобальная оптимальность не гарантируется.
Для положительного требуемого запаса NPSH нужна соответствующая характеристика насоса.

В периоде расписания `unavailable_pumps` задаёт недоступные агрегаты; отсутствие
поля сохраняет прежнее значение, пустой список снимает недоступность.
`station_target_pressure_pa` меняет уставку станции. Ручное управление скоростью
регулируемых насосов отклоняется как конфликт. JSON checkpoint включает состав
станции, накопления, контрольную сумму и отпечаток модели/расписания.

API FIM: `set_surface_controls`, `set_surface_pressure_control`,
`set_surface_station(selection)`. Рецепт станции привязан к отпечатку сети;
выбранный состав фиксирован внутри Ньютона, скорость решается заново.
`set_surface_station(None)` возвращает исходную сеть доступных агрегатов.
Автоматический перебор состава не выполняется на каждой итерации Ньютона.

## Управляемые сопротивления black-oil

В `homogeneous_blackoil_tree` у ветвей `pipes` допустимы `loss_coefficient`
(K >= 0) и `valve_opening` (0 < a <= 1). Эффективное K/a² распределяется
по длине ветви; это не специализированная корреляция локального штуцера.
Для изменения открытия нужен K > 0. Закрытие до нуля отклоняется до реализации
статического удержания фаз. Старые конфиги эквивалентны K=0, a=1.

В black-oil `physical_surface_network` добавлены `controls.valve_openings`
и `pressure_control`: `valve`, `node`, `target_pressure_pa`, `min_opening`
(по умолчанию 0.2), `max_opening` (1), `pressure_tolerance_pa` (1e-4 Па),
`max_evaluations` (50). Узел регулирования должен быть выше управляемой ветви
по направлению к источникам. Регулятор учитывается неявно в производных FIM.
Предел открытия допускает отклонение фактического давления от уставки.

У `GatheringFacility` тот же `pressure_control` задаётся рядом с `gathering`.
В расписании `gathering_valve_openings` обновляет карту ручных открытий,
`gathering_target_pressure_pa` обновляет уставку. Команды сохраняются;
ручное управление ветвью регулятора запрещено.
Примеры: `configs/fim_blackoil_surface_regulated.json`,
`configs/surface_gathering_active_schedule.json`.
Подробная физическая область: [black-oil оборудование](BLACKOIL_ACTIVE_EQUIPMENT.md).

## Локальные жидкостные клапаны black-oil

В `homogeneous_blackoil_tree` необязательный список `valves` содержит отдельные
ветви: `name`, `start`, `end`, `diameter_m`, `loss_coefficient`,
`vapor_pressure_pa`, `pressure_recovery_factor`, `valve_opening` (по умолчанию 1).
Порты должны иметь одинаковые отметки. K, диаметр и давление пара положительны,
0 < F_L <= 1 и 0 < opening <= 1. K/opening² применяется локально с плотностью
на входе; распределённые сопротивления труб по-прежнему задаются в `pipes`.

Свободный газ проверяется на входе, выходе и в сжатом сечении; проверяются
давление пара и изменение плотности <=1%. Неподдерживаемый режим отклоняется.
Это ограниченная жидкостная модель, а не газожидкостный критический штуцер.
Коэффициенты и давление пара — исходные данные оборудования при заданной температуре.

Регулятор и команды открытий общие с распределёнными сопротивлениями.
Примеры: `configs/fim_blackoil_surface_local_valve.json`,
`configs/surface_gathering_local_valve.json`,
`configs/surface_gathering_local_valve_schedule.json`.
Диагностический `scripts/run_fim_blackoil_surface.py` принимает `--initial-rs`
(м³/м³), требующий нулевой начальной газонасыщенности и Rs <= насыщенного.
Для FIM-примера: `--initial-rs 25 --outlet-mpa 1.2 1.4 1.6 --days 5`.
Полное описание: [локальный клапан](BLACKOIL_LOCAL_VALVE.md).

## Газовый экспорт с конечным проходным сечением

В `gas_export` добавлен необязательный `export_valve`: `name`,
`outlet_pressure_pa`, `throat_area_m2`, `discharge_coefficient` (по умолчанию 1),
`max_opening` (1). Давление, площадь и Cd положительны; Cd <= 1 и
0 <= max_opening <= 1. Линейный закон эффективной площади Cd*A*opening
относится к эквиваленту сопла сухого идеального газа, не к универсальному IEC клапану.
Элемент расположен после экспортной трубы; давление на входе берётся из её расчёта.

Фактическое открытие вычисляется под заданную подачу и противодавление.
Если пропускной способности не хватает, возникает физическая ошибка;
внешний ограничитель `FacilityCapacityControl` может уменьшить подачу.
Противодавление выше входного при положительном расходе отклоняется.
В критическом режиме расход не зависит от дальнейшего снижения противодавления.

`SurfaceFacility.run` и `FacilityPeriod` принимают `gas_valve_max_opening`
и `gas_valve_outlet_pressure_pa`. Значения расписания сохраняются до следующей
команды. Даже на остановке команды без настроенного газового клапана отклоняются.
Полное закрытие допускается как настройка остановки; для положительного расхода
оно не создаёт фиктивного потока. Водяное `valve_openings` независимо.

Примеры: `configs/surface_gas_valve_facility.json`,
`configs/surface_gas_valve_schedule.json`. Формулы, производные, неоднозначность
обратного давления на критической полке и физические границы:
[газовый элемент экспорта](GAS_EXPORT_VALVE.md).

## Обратная связь площадки с FIM

`simulation.coupled_facility` содержит `facility` (обычная конфигурация
`SurfaceFacility`) и необязательный `control`: `min_fraction` (0.001),
`fraction_tolerance` (1e-4), `scan_points` (9), `max_evaluations` (60).
Требуется физическая black-oil FIM-связь с добывающим деревом.
Приёмник дерева и первая ступень сепарации должны совпадать по давлению,
PVT/PVTO и стандартным плотностям. Площадка получает фактические компонентные
потоки скважин; её шаблонные `feeds` не добавляются к добыче.

При ограничении ресурсов внешний поиск меняет общий множитель верхних
пределов дебитов и заново решает тот же подшаг FIM. Допуск множителя абсолютный.
Исходные операторские уставки сохранены, применённые уставки и все пробы
попадают в отчёт. Численный отказ не считается физическим ограничением.
Общий контур не является монолитным якобианом площадки; в ограниченном режиме
стоимость составляет несколько полных пластовых решений на подшаг.

Пример: `configs/fim_blackoil_facility_coupled.json`, запуск через
`scripts/run_fim_blackoil_surface.py --outlet-mpa 1.0 --days 5`.
Модель пока ограничена положительной добычей без ramp/нагнетателей/MSW;
газожидкостный критический штуцер, термический flash и динамика аппаратов
не реализованы. [Подробности и проверки](FIM_FACILITY_COUPLING.md).
