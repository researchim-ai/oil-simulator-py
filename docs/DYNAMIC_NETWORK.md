# Связанная динамическая сеть сосудов

`DynamicVesselNetwork` объединяет [динамические равновесные сосуды](DYNAMIC_VESSEL.md)
в одно неявное решение. Все аппараты используют одинаковые явные компоненты,
критические параметры, kij, калорику и опорные состояния PR. Общие часы обязательны.
Поддержаны несколько соединений, кольца, обратные потоки и фазовые порты.

## Совместное решение

На новом временном слое для каждого сосуда решаются компонентные запасы,
давление и температура. Как у отдельного аппарата, внутренняя энергия
получается из фазового равновесия, а объём остаётся постоянным.
Потоки соединений зависят от **новых**, а не предыдущих давлений.
Состав и энтальпия выбираются из нового состояния фактического донора.

Один компонентный/энтальпийный перенос вычитается из донора и прибавляется
получателю. Кинетическая энергия соединения и запас вещества в нём не
рассчитываются; это предельный случай короткой пассивной связи без linepack.
Возможное изменение фаз принимаемого вещества входит в равновесие общего
запаса получателя, без ручной коррекции состава.

Система решается монолитно с межаппаратными зависимостями через давления,
составы фаз и энтальпии. Это не последовательный обмен старым расходом между
независимыми расчётами. EOS-состояния неизменённых локальных блоков повторно
используются при конечных разностях, чтобы не пересчитывать все сосуды
при возмущении одной неизвестной.

Проверяются компонентные, энергетические и дискретные энтропийные балансы
каждого сосуда, а также компонентный/энергетический баланс границы сети.
Внутренний перенос сокращается из общего баланса. Накопления расписания
содержат только внешние подачи, отборы и тепло.

## Линейная модель соединения

`VesselConnection` требует:

- `name`, `source`, `target` — уникальное имя связи и имена двух разных сосудов.
- `molar_conductance_mol_s_pa` — положительная молярная проводимость C.
- `max_pressure_difference_pa`, `max_molar_rate_mol_s` — границы применимости.
- Необязательные `source_port`, `target_port`: `bulk`, `phase_0`, `phase_1`.
- `allow_reverse` (false) — разрешение обратного потока.

```
N_dot = factor C (P_source - P_target)           # allow_reverse=true
N_dot = factor C max(P_source - P_target, 0)    # allow_reverse=false
```

Положительный знак соответствует направлению source→target. При обратном
потоке донор — target, и его `target_port` определяет состав/энтальпию.
При нулевом расходе фазовый перенос не выдумывается.

Это **заданная линейная характеристика**, а не универсальная газовая
гидравлика или sizing клапана. Для рабочего случая C нужно определить и
проверить по данным в ожидаемой области P/T/состава. Реализация контролирует
заданные границы перепада и расхода; она не калибрует C и не задаёт автоматически
его температурную/композиционную зависимость.

При превышении границ начальное или принятое состояние отклоняется;
расход не обрезается до максимума. Математические пробы нелинейного решателя
могут использовать продолжение линейной функции за границу, но физический
принятый режим обязан лежать внутри неё. Это не критическая полка штуцера.
Предел перепада — область характеристики при течении, не паспортная прочность
закрытого клапана. Для factor=0 перенос отсутствует, механический расчёт отсутствует.

`connection_factors` задаёт множитель проводимости от 0 до 1 по имени связи.
Это явное управление коэффициентом, не универсальная корреляция открытия
реального клапана. Для связи без привода ноль закрывает связь сразу, а изменения применяются
на границе периодов. Опциональный [привод](CONNECTION_ACTUATORS.md)
преобразует команду в фактическое положение с конечной скоростью. Опциональные событийные отключения
задаются [правилами защиты](NETWORK_PROTECTIONS.md).

## Области и отказ

Фазовые порты имеют те же соглашения, что в отдельном сосуде: в двухфазном
режиме первая фаза — жидкость, вторая — пар. Положительный расход из
отсутствующего порта отклоняется; скрытой замены на bulk нет.
Изменения фаз при текущей итерации могут вызвать отказ/дробление шага;
полный поиск фазовых событий с переключением команд пока не реализован.

Пассивная внешняя подача требует достаточного давления источника.
Внешний расход задан, характеристика входной арматуры не решается.
Каждый сосуд сохраняет свои границы давления, минимальных запасов,
температурного диапазона и объёмной доли жидкости.

Один общий подшаг принимается только при сходимости и допустимости **всех**
аппаратов/связей. При отказе уменьшается шаг всей сети. Интервал проходит
полностью либо возвращает ошибку; состояния вызывающей стороны неизменны.
Backward Euler имеет первый порядок; state-change guards не заменяют оценку
погрешности и проверку временным сгущением.

## Python API

```python
from surface import DynamicVessel, DynamicVesselNetwork, VesselConnection

vessels = {
    "a": DynamicVessel("a", 0.01, 1e5, 5e6),
    "b": DynamicVessel("b", 0.01, 1e5, 5e6),
}
network = DynamicVesselNetwork(vessels, (
    VesselConnection("line", "a", "b", 1e-7, 2e6, 0.2, allow_reverse=True),
))
# C и пределы здесь демонстрационные; это не данные реального клапана.
states = {
    "a": vessels["a"].initialize(fluid, 2e6, 300, [0.3, 0.7]),
    "b": vessels["b"].initialize(fluid, 1e6, 300, [0.7, 0.3]),
}
result = network.advance(states, fluid, duration_s=1, initial_dt_s=0.5)
```

`feeds`: имя сосуда → последовательность `ThermalStream`.
`withdrawals`: имя сосуда → отображение фазовых портов в mol/s.
`heat`: имя сосуда → `heat_w`, `utility_temperature_k`.
`connection_factors`: имя связи → коэффициент [0,1].
Неизвестные имена и параметры отклоняются. В истории шага сохранены состояния
всех сосудов, знаковые расходы связей, фактические доноры/получатели,
компонентные переносы, энтальпии и невязки.

## Расписание и JSON

`run_network_schedule` использует общие канонические контрольные суммы и
суммирование принятых потоковых интегралов существующего модуля сосудов.
Checkpoint содержит все запасы/P/T/энергии/часы, связи, принятые шаги и
внешние накопления. Проверяются отпечатки исходной модели/геометрии/связей/
команд/реализации, checksum, часы, накопления и баланс всей границы.
Контрольная сумма выявляет повреждение данных, не является цифровой подписью.

`configs/surface_vessel_network.json` содержит:

- `fluid`: `components`, `binary_interactions`.
- `vessels`: имя → параметры `DynamicVessel` без дублирования `name`.
- `connections`: список полных `VesselConnection`.
- `initial`: имя сосуда → `pressure_pa`, `temperature_k`, `mole_fractions`,
  необязательный `time_s` (одинаковый у всех).
- `periods`: список `duration_s`, необязательных `feeds`, `withdrawals`,
  `heat`, `connection_factors`.
- `stepper`: необязательные `initial_dt_s`, `maximum_dt_s`, `minimum_dt_s`,
  `max_substeps`, с теми же соглашениями, что у отдельного сосуда.

В периодном JSON `feeds` — имя сосуда → имя подачи → PT/молярный расход/состав.
Все команды полны относительно периода: неуказанный factor снова равен 1,
тепло/внешний отбор/подача отсутствуют, а не наследуются неявно.

```bash
python scripts/run_vessel_network.py configs/surface_vessel_network.json --output /tmp/network.json --stop-after 1
python scripts/run_vessel_network.py configs/surface_vessel_network.json --checkpoint /tmp/network.json --output /tmp/network.json
```

CLI записывает файл атомарно после успешного вызова. Ошибка не повреждает
исходный checkpoint. Это транзакция одного вызова, не непрерывное автосохранение.

## Проверка и ограничения

Проверяются один сосуд против исходного решателя, перенос по новым давлениям,
прямое/обратное течение, закрытая связь, кольцо, независимость от порядка
перечисления, фазовый перенос, полный интервал после дробления, команды,
баланс внешней границы и точное JSON-продолжение.

CPU reference. Нет водной фазы, инерции/запаса труб, нелинейной многофазной
гидравлики длинных связей, отдельных температур фаз,
полного поиска фазовых событий, сопряжения с FIM
или GPU. PR использует демонстрационные постоянные Cp/kij и ограниченный
численный поиск устойчивости. Перенос на реальный промысел требует физических
свойств, характеристик соединений и независимой валидации.

## Нелинейное однофазное PR-сопло

Вместо линейной связи можно явно выбрать `PRNozzleConnection` или JSON
`model: "pr_single_phase_nozzle"`. Расход вычисляется из PR-энтропии,
энтальпии, плотности и местной скорости звука; постоянная gamma и
идеальногазовая формула вместо PR не подставляются.

Для выбранного состава фазы-донора решается однородный PS-путь. Каждое
использованное состояние проверяется полным PT-flash смеси: вход или
изоэнтропа, требующие нескольких фаз, вызывают отказ. Даже если входной
сосуд двухфазный, явно выбранный фазовый порт может быть однофазным;
при конденсации/испарении на пути этой связи нужен явно выбранный HEM-режим,
а не скрытая замена bulk на пар или линейную проводимость.

Из EOS аналитически получаются Cv, Cp, производные объёма и скорость звука.
Для постоянного состава и механически устойчивого корня:

```
Cp - Cv = -T (dP/dT|v)^2 / (dP/dv|T)
a_sound^2 = -v_m^2 / M * (Cp/Cv) * (dP/dv|T)
u(P)^2 = 2 [h0 - h(P,s0)]
```

Сначала ищется первый sonic-переход на ветви, связанной с дозвуковым входом:
`u = a_sound`. Ниже разрешённого критического давления расход перестаёт
зависеть от противодавления. Однофазный принцип критического истечения
обсуждается в [NASA — methane/natural-gas critical nozzles](https://ntrs.nasa.gov/api/citations/19710011855/downloads/19710011855.pdf).
Это модель термодинамического истечения, не ISO/IEC-сертифицированный sizing.

`minimum_pressure_ratio` ограничивает поиск вниз от входного давления.
Если sonic-состояние не разрешено, критическое давление не выдумывается:
поддержан только разрешённый докритический путь. Состояния ниже найденной
горловины для дозвукового поиска не требуются. При нарушении однофазной области
поиск может уточнять границу допустимой ветви; он не заменяет состояние
двухфазной аппроксимацией. Полный анализ неклассических многократных sonic-ветвей
и глобальный сертификат максимального потока не заявляются.

`connection_factors` здесь масштабирует **эффективную площадь**, а не C.
Направление, выбор фактического донора и фазового порта совпадают с линейной
связью. Поток вычисляется по новым давлениям, T и составу; межаппаратные
производные входят в численный неявный якобиан. При критическом истечении
малое изменение противодавления не меняет расход, пока режим не сменился.

В сеть передаётся компонентный поток с исходной полной энтальпией фазы-донора:
кинетическая энергия струи диссипирует при смешении в принимающем сосуде.
Отдельного запаса/кинетической энергии сопла нет. У отдельного
`PRSinglePhaseNozzle.run` выводятся изоэнтропийная горловина и, по умолчанию,
смешанный PH-выход с исходной энтальпией. Эти два состояния не отождествляются.

Параметры JSON-связи:

- `model`: `pr_single_phase_nozzle`.
- `name`, `source`, `target`, `source_port`, `target_port`, `allow_reverse`.
- `throat_area_m2`, необязательный `discharge_coefficient` (1).
- `minimum_pressure_ratio` (0.4), `pressure_tolerance_pa` (0.001).
- `max_pressure_difference_pa`, `max_molar_rate_mol_s` — обязательные
  границы допустимой работы, не обрезание потока до максимума.

Старые JSON-связи без `model` по-прежнему линейные. Неизвестная модель или
параметр отклоняются. Демонстрационный файл:

```bash
python scripts/run_vessel_network.py configs/surface_vessel_network_pr_nozzle.json --output /tmp/sonic-network.json
```

Критические состояния повторно используются в пределах одного нелинейного
шага только при точно совпадающих EOS, P/T и составе донора и параметрах
поиска. Противодавление не входит в ключ ёмкости критической ветви;
докритическое состояние вычисляется для фактического противодавления.
Нет приближённой интерполяции или скрытого устаревшего состояния донора.
Счётчик `eos_evaluations` сети относится к состояниям самих сосудов;
дополнительная работа поиска сопла в него не включена.

Независимые проверки: идеальногазовый предел, аналитические Cp/Cv против
производных и чистого вещества, акустика против PS-конечных разностей,
расход/критическое давление против общего HEM-расчёта в общей однофазной
области, критическая полка и неявная сеть с JSON-продолжением.
Это CPU-реализация, без воды/проскальзывания/двухфазной горловины,
геометрии реального клапана или экспериментальной калибровки Cd/калорики.

## Двухфазная HEM-связь

`HEMNozzleConnection`, JSON `model: "pr_hem_nozzle"`, включает существующее
равновесное сопло смеси непосредственно в монолитный шаг сети. Входной
порт и горловина могут содержать одну или две фазы. В том числе допустим
однофазный вход, который вскипает/конденсируется на изоэнтропическом пути.
Однофазный PR-режим автоматически на HEM не переключается: модель выбирается явно.

Состав переносимого компонента определяется портом донора, а не фазой,
появившейся в горловине. Фазы HEM имеют одинаковую скорость и мгновенно
достигают теплового/химического равновесия; компонентный состав общего
переноса сохраняется. Скорость/плотность горловины задают массовый расход,
а в принимающий сосуд поступает полная энтальпия исходного порта.
Вода, проскальзывание и задержка вскипания этим приближением не добавляются.
Обсуждение HEM и отличий от неравновесных моделей:
[Waxman et al., AIAA 2013-3636](https://web.stanford.edu/~cantwell/Selected_Publications/Liquifying%20hybrid%20fuels%2C%20hybrid%20rocket%20design%2C%20small%20thrusters%2C%20propulsion%20designs%20for%20Mars/Mass%20Flow%20Rate%20and%20Isolation%20Characteristics%20of%20Injectors%20for%20Use%20with%20Self-Pressurizing%20Oxidizers%20in%20Hybrid%20Rockets%20AIAA%202013-3636.pdf).

Вместо sonic-условия для однофазного звука используется максимум массового
потока HEM на PS-пути, с уточнением найденных фазовых границ. Поэтому
двухфазные Mach/скорость звука не выдумываются. В журнале связи:
`upstream_port_phase_count`, `throat_phase_count`,
`throat_vapor_molar_fraction`, критическое давление и флаг его разрешения.
Критическая полка, неразрешённый максимум на нижней границе и обнаруженные
множественные максимумы обрабатываются как у самостоятельного HEM-сопла.

Параметры связи:

- `name`, `source`, `target`, `source_port`, `target_port`, `allow_reverse`.
- `throat_area_m2`, `minimum_pressure_pa` — обязательны.
- `max_pressure_difference_pa`, `max_molar_rate_mol_s` — обязательные ограничения.
- `discharge_coefficient` (1), `scan_points` (9), `pressure_tolerance_pa` (0.01).

`minimum_pressure_ratio` относится к однофазной модели и здесь не используется.
Весь исследуемый PS-диапазон должен быть допустим, противодавление не ниже
`minimum_pressure_pa`. `connection_factors` масштабирует площадь.

```bash
python scripts/run_vessel_network.py configs/surface_vessel_network_hem.json --output /tmp/hem-network.json
```

### Невязка, якобиан и повторное использование

Физическая невязка каждой нелинейной итерации и окончательная проверка
используют **полный** HEM-поиск расхода. Для точно совпадающих EOS/P/T/состава
и параметров поиска повторно используются PS-состояния и критическая ёмкость.
Изменение донора, его состояния или области поиска требует нового расчёта;
интерполяции между разными состояниями нет.

В якобиане гладкой внутренней критической ветви используется стационарность
`dG/dPcrit=0`: производные расхода по входным P/T/составу вычисляются при
фиксированном найденном критическом давлении, без нового максимизационного
поиска для каждого малого возмущения. Для докритического потока учитывается
производная по противодавлению. Точная величина расхода в базовой точке
берётся из полного поиска; касательная не подменяет поток принятого состояния.

Проверяются центральная и односторонние производные по давлению горловины,
область фаз и конечность производных. Вблизи появления/исчезновения фазы,
при негладком максимуме, границе диапазона или неразрешённом касательном
расчёте используется полный численный якобиан той же HEM-модели.
Это возврат к более дорогому вычислению производной, не к другой физике.
Невязки и допуски принятия шага не ослабляются.

Для HEM-блока относительное возмущение численного якобиана задаётся отдельно
от точности самой невязки, чтобы ошибки вложенного поиска не доминировали
в производной. PS-поиск в касательных получает необязательный
`temperature_guess_k`: начальная скобка расширяется до допустимой области,
если нужно. Проверка фаз, целевое уравнение и конечный допуск прежние;
неверная температурная подсказка отклоняется.

У самостоятельного `MixtureEquilibriumNozzle.run` `with_outlet=True`
сохраняет прежний PH-выход и проверку энергии смешения. Внутри сети
`with_outlet=False`: отдельный пустой PH-объём не создаётся, принимающий
сосуд сам решает смешение и свой энергетический/энтропийный баланс.
Неприменимые отдельные выходные диагностические величины возвращаются как null.

### Границы подтверждения

Проверены точный кэш, критическая полка, смена фаз на пути, производная
критического расхода против полного поиска, двухфазный общий шаг,
свежий физический replay, обратное направление, закрытие, JSON-перезапуск.
Сетка давления и TPD-поиск конечны, глобальная устойчивость/все экстремумы
математически не сертифицируются. Новая связанная реализация остаётся
CPU reference и существенно дороже однофазного sonic-режима.
Экспериментальная точность двухфазного расхода и применимость HEM к конкретной
геометрии требуют отдельной валидации. Полноценный нефтегазоводяной штуцер,
linepack, инерция/неравновесность, GPU и связь с пластовым FIM остаются за областью.


[Событийные защиты](NETWORK_PROTECTIONS.md) локализуют пороги по давлению,
температуре, запасу и жидкому объёму с повторным физическим расчётом до события.
Они добавляют отключения, защёлки/ручной сброс и сохранение состояния защиты
между периодами и в checkpoint; это отдельный опциональный режим.

## Тепловая инерция стенок

Опциональные стенки с отдельным запасом энергии решаются в общем неявном
шаге. Конфигурация, баланс, продолжение и тепловой выбег после защиты описаны
в [руководстве по стенкам](VESSEL_WALL.md).
