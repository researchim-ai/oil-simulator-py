# Насос, привод, сеть и регулятор

`DynamicPumpNetwork` совместно рассчитывает один управляемый центробежный
насос, инерцию его вала и существующую жидкостную сеть. PI/PID обновляется
по отдельному цифровому такту. Нагрузка насоса не замораживается из прошлого
шага: при поиске новой скорости заново решаются расход и давления сети.

Это модель динамики **вала с квазистационарной гидравликой**. Запасы жидкости,
сжимаемость трубопровода, гидроудар и температура жидкости в ней не являются
неизвестными. Её нельзя выдавать за распределённую переходную модель труб.

## Поддерживаемая схема

Требуются `LiquidNetwork`, `RotatingDrive`, номинальная угловая скорость
и один открытый насос с обратным клапаном. Используются существующие
квадратичные или табличные характеристики напора, КПД, NPSH и мощности.
При нулевой скорости насос считается изолированным; обратное вращение
и турбинный режим в этот блок не входят.

Сеть питается заданными давлениями; фиксированные узловые расходы при
запуске не поддерживаются. В каждом отсоединённом при остановке участке
должен оставаться опорный узел давления. Изолированному замкнутому объёму
для определения давления нужна отдельная модель запасов/сжимаемости.
Разрешены изменения граничных давлений и открытий существующей арматуры.

## Совместный подшаг и энергия

Для каждого подшага решается скалярное уравнение скорости:

```
ω_mid = (ω_old + ω_new)/2
J (ω_new−ω_old)/dt = τ_motor − P_shaft(ω_mid, network)/ω_mid − b ω_mid
```

Внутри вычисления P_shaft решается вся гидравлическая сеть с новой средней
скоростью насоса. В покое момент насосной нагрузки определяется как ноль,
без деления на нулевую скорость. Давления и расходы конечного состояния
вычисляются отдельно от средних потоков, использованных в балансе.

Умножение уравнения на ω_mid dt даёт точный дискретный баланс изменения
кинетической энергии. Учитываются:

- электрическая энергия, работа двигателя и его потери;
- работа на валу насоса, гидравлическая работа и потери насоса;
- вязкие потери вала, потери труб и арматуры;
- гидравлическая работа, переданная через граничные узлы, включая высоты.

Тепло записывается в журнал, а не удаляется из баланса. Но температура
жидкости не пересчитывается: это изотермическая модель с отводом выделенного
тепла. Для передачи этого тепла в PR-сеть требуется отдельное сопряжение.

`no_flow_power_w_at_nominal` задаёт дополнительную мощность вращающегося
насоса при нулевом расходе; масштабирование — P0 (ω/ω_nom)^3.
Ей соответствуют момент нагрузки и выделение тепла, в том числе когда
обратный клапан блокирует расход. По умолчанию P0=0, а не выдуманная
паспортная мощность. Суммарная мощность проверяется по пределу насоса.
Этот параметр не превращает произвольную многорежимную машину в
калиброванную модель; его нужно получать из данных оборудования.

При торможении определяется подшаг достижения покоя, затем учитывается
идеальный удерживающий упор. В отличие от отдельного аналитического
`RotatingDrive`, время остановки здесь аппроксимируется совместной
схемой средней точки и уточняется при уменьшении шага.

## PID и режимы

`PIDController` поддерживает P, PI и PID. Выход — момент в N m.
В `DynamicPumpNetwork` доступны измерения `pressure` (Pa), `flow` (m³/s)
и `speed` (rad/s). Для давления требуется имя узла `measurement_node`;
регулировать внешне зафиксированное давление нельзя.

Параметры: `proportional_gain`, `integral_gain`, `derivative_gain`,
`min_output`, `max_output`, `bias`, `direction`, `derivative_filter_s`,
`tracking_time_s`. Для обратного действия используется direction=−1.
Для давления единицы коэффициентов P/I/D соответственно N m/Pa,
N m/(Pa s), N m s/Pa. Коэффициенты примера синтетические, не универсальная
настройка для любого насоса.

Производная берётся по измерению и фильтруется: скачок уставки не создаёт
D-kick. Anti-windup учитывает внутреннее насыщение и фактически приложенный
момент предыдущего такта, включая внешние пределы мощности/скорости.
При переходе manual/off→auto интегратор отслеживает реально приложенный
выход; первый автоматический такт не создаёт скачка команды.

Режимы периода:

- `auto`: регулирование уставки;
- `manual`: заданный момент с ограничениями;
- `off`: двигатель обесточен, вал продолжает выбег;
- `trip`: обесточивание и установка защёлки. Последующий запрос auto
  не включает двигатель до явного `reset_trip=true`.

`trip` — моделируемая операторская команда/вход защиты, не автоматическое
обнаружение всех аварий и не сертифицированная система безопасности.
Ограничения момента, мощности потребления/рекуперации и максимальной
скорости применяются с явным учётом фактической работы. Уставка при этом
может остаться недостигнутой: результат содержит конечную ошибку регулирования.
Нарушения допустимых характеристик насоса, NPSH, области свойств или
определимости давления возвращают ошибку, а не притворяются успешной защитой.

## Время, повторы и restart

`control_interval_s` задаёт такт контроллера. `maximum_dt_s`,
`minimum_dt_s`, `max_speed_change_rad_s` — внутреннее разбиение динамики.
При отказе нелинейного расчёта/баланса шаг дробится, но PID не вычисляется
повторно. Двигатель держит команду на протяжении такта; обратная связь
по фактическому моменту усредняется по принятым подшагам.

Каждый период заканчивается в запрошенное время; дробление не сокращает
отчётный интервал. На границе периода начинается новый такт управления,
что позволяет однозначно применять новую команду/уставку. Произвольное
разбиение периода пользователем может изменить сетку цифровых тактов;
проверяемый restart выполняется на границах сохранённых периодов.

`network_options` периода не наследуются: они задают изменения относительно
базовой сети именно на этот период. Если давление должно сохраняться,
повторите override в следующих периодах.

Checkpoint хранит скорость, время, память PID, фактический момент и защёлку.
Проверяются checksum, параметры, расписание, исходники, версии NumPy/SciPy,
часы, путь скорости, работы и накопленная энергия. Контроллерная история
воспроизводится без повторного расчёта всей старой гидравлики. Изменённые
исходники или модель не принимаются как совместимый checkpoint.
CLI пишет JSON атомарно.

## Пример и независимая проверка

`configs/surface_dynamic_pump.json`: запуск с нуля и поддержание давления,
ручной режим, новая уставка с изменением противодавления, отключение trip,
попытка включения без сброса, затем сброс и торможение.

```bash
python scripts/run_pump_drive.py configs/surface_dynamic_pump.json --output results/dynamic_pump/full.json
python scripts/run_pump_drive.py configs/surface_dynamic_pump.json --stop-after 3 --output results/dynamic_pump/partial.json
python scripts/run_pump_drive.py configs/surface_dynamic_pump.json --checkpoint results/dynamic_pump/partial.json --output results/dynamic_pump/resumed.json
cmp results/dynamic_pump/full.json results/dynamic_pump/resumed.json
python scripts/check_dynamic_pump.py --output results/dynamic_pump/reference.json
```

Независимый эталон объединяет формулу Пуазейля, аналитическое решение
квадратичной характеристики и высокоточное интегрирование ОДУ вала.
Уменьшение подшага вдвое даёт примерно четырёхкратное уменьшение ошибки
при постоянной команде. Это второй порядок динамики вала с сетью,
а не заявление о втором порядке непрерывного PID: регулятор дискретный
и имеет собственный неизменный такт.

## Что остаётся за пределами блока

Группы динамических насосов реализованы отдельной
[параллельной станцией](DYNAMIC_STATION.md). Многоквадрантные характеристики,
реальные карты электрического привода, PR/многофазные компрессоры, динамические
запасы и энергия труб, единая PR/FIM-связь и GPU — следующие отдельные
задачи. Реальных паспортных данных для калибровки пока нет.
Протокол: `reports/validation/2026-11-02/DYNAMIC_PUMP_VALIDATION.md`.

Карта компрессора и антипомпажный контур для сухого идеального газа
реализованы в отдельном [газовом блоке](COMPRESSOR_TRAIN.md).
