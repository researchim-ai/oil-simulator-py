# Пакетная гидравлика black-oil сборного дерева

`BlackOilProductionNetwork` поддерживает опциональный `hydraulic_backend`:
`scalar` (по умолчанию) или `torch_batch`. Параметр задаётся внутри
`physical_surface_network.network`, а не рядом с `well_block_backend`.
Положительный целый `pipe_batch_size` от 1 до 256 (по умолчанию 128)
задаёт верхний размер пакета. Старые checkpoints без этих атрибутов
используют скалярный путь. Сериализация и смена статических открытий
сохраняют выбранную численную политику.

```json
{
  "simulation": {
    "physical_surface_network": {
      "well_block_backend": "tree_structured",
      "network": {
        "hydraulic_backend": "torch_batch",
        "pipe_batch_size": 128
      }
    }
  }
}
```

Это фрагмент настроек: остальные обязательные поля модели сохраняются.
Backend применим и с плотным скважинным блоком; `tree_structured`
нужен для больших чисел скважин, но не является условием пакетной трубы.

## Что вычисляется

Сохраняется существующая изотермическая homogeneous Rs-only постановка
`BlackOilPipe`. Пакет объединяет **независимые трубы одного уровня дерева**:
давление их выходов уже известно, давление входов определяется интегралом
импульса в координате давления. Трубы могут иметь разные диаметры,
длины, подъёмы, шероховатости, K и компонентные расходы.

Используются прежняя интерполяция PVT/PVTO, равновесное выделение газа,
переходная ламинарно-турбулентная корреляция и итерационный Colebrook.
Во всех строках остаются float64 и независимые компоненты oil/water/gas.
Плотная матрица по трубам не строится. Локальные клапаны и одиночные трубы
(например общий коллектор) проходят через существующие модели.

Квадратура разбивается по фиксированным узлам всех PVT-таблиц и собственной
движущейся точке насыщения каждого потока. Обрезанные и отсортированные
границы задают отдельные сегменты; вырожденные сегменты имеют нулевую длину.
Проверяются последовательные порядки Gauss 16/32/64/128/256. Допуски
сохранены: абсолютные 1e-7 для длины и 1e-8 для двух интегралов энергии,
относительный 1e-9. Сложная строка может заставить весь пакет повториться
по скалярному пути с его рекурсивным дроблением интервала и теми же
допусками, без ослабления точности.

Для обращения давления строится ограниченная PVT-диапазоном скобка,
а начальное давление прогнозируется по уже вычисленному локальному
градиенту импульса в известном порту: `p_out + length * dp_dx`.
Если прогноз нечисловой или вне скобки, используется её середина.
Это только начальное приближение; интегральное уравнение, критерии
квадратуры и финальные физические проверки сохранены. Дополнительного
скалярного опроса CUDA или переноса свойств на CPU не добавлено.
Аналитический предел Пуазейля, CPU/CUDA-производные и сохранение
связанного месячного решения проверены отдельно.
[Результаты оптимизации стартового давления](../benchmarks/reports/surface_pipe_initialization/README.md).
Скалярный путь дополнительно переиспользует отсоединённые длины
интеграла для точно одинаковых давлений внутри одного `_solve`.
Кэш не переносится в другой расчёт, исключения и AD-графы не сохраняются;
финальный интеграл с чувствительностями вычисляется независимо.
Затем используется Newton с возвратом в скобку. Производная интеграла
по давлению вычисляется autograd. Итерации поиска давления не входят в
граф чувствительности: после нахождения корня невязка интеграла ещё раз
дифференцируется по обоим давлениям, трём компонентным массам и K;
неявная теорема даёт те же пять выходных производных, что у скалярной
трубы. Между независимыми строками нет производных.

## Проверки и повторный расчёт

Сохранены входная проверка состава и непрерывности PVTO, допустимость
ускорительного множителя, контроль остатка длины, механического баланса
и конечности чувствительностей. Пакет не объявляет физический choking
или выход из PVT-диапазона допустимым решением. Если его ограниченный
алгоритм не справляется, он повторяет трубы существующим скалярным
решателем; его физическая или численная ошибка передаётся вызывающему
коду. Успешный скалярный повтор явно помечается `scalar_retry`.

Отчёт дерева `hydraulic_execution` содержит backend и числа труб:
`torch_batch_pipes`, `scalar_retry_pipes`, `scalar_pipes`. Это счётчики
конкретного solve, а не накопленная стоимость всех итераций Newton/FIM.

Размер пакета дополнительно ограничивается оценкой числа точек квадратуры
на максимальном порядке: `(fixed_knots + 2) * 256 * batch <= 2000000`,
где `fixed_knots` — максимальное число различных узлов общей PVT-оси
и одной пары соседних PVTO-таблиц,
кроме минимальной одиночной строки. Это ограничение одной сетки точек,
не строгий предел общей памяти autograd/PVTO. Для большого числа Rs-таблиц
и глубоких деревьев нужен отдельный ресурсный замер.

## Подтверждённая область и границы

Тесты сопоставляют состояния и их производные с прежней термодинамикой,
давления/пять чувствительностей/энергию с отдельными скалярными трубами,
компонентные производные с конечными разностями и сохранённый сценарий
появления газа. Проверяются также межскважинные производные целого дерева,
смена статических управлений, явный скалярный повтор и настоящий choking.
Полные FIM-прогоны сравниваются при одинаковых физических конфигурациях
и независимо проверяемых компонентных балансах.

Это ускорение численного представления, не новая физическая корреляция
и не экспериментальная калибровка. Сохраняются ограничения дерева:
нет реверса, статического нулевого потока, расщепления потока, нисходящих
труб, slip/holdup или распределённой тепловой динамики этой ветви.
Другие модели проекта этим backend не подменяются.

Алгебра пакета написана на PyTorch и допускает устройство модели; CUDA
тест предусмотрен. В текущем окружении драйвер NVIDIA недоступен, поэтому
квалификация скорости выполнена на CPU. Проверки входов выполняются пакетом: покрытие PVT/PVTO, непрерывность
Bo/mu_o в движущейся точке насыщения и наличие zero-GOR PVTO для
производных чистой воды. Возвращается один host-пакет из пяти статусов
на пакет труб; отдельные `float/int/bool` для строк не используются.
Массы и давления могут уже находиться на устройстве. Для host-входов
создаются целые тензоры пакета вместо загрузки каждой строки.
Одиночные скалярные трубы/повторы, топологическая оркестрация и
формирование отчёта сохраняют host-операции. Полностью автономный
GPU-промысел и ускорение Norne этим результатом не подтверждены.

[Протокол и воспроизведение](../benchmarks/reports/surface_pipe_batch/README.md).

## Дополнительная оптимизация входных проверок

`blackoil_batch_admission.validate_inputs` сохраняет проверки старого
построчного допуска и выполняет их тензорно. Безопасные значения для
неактивного PVT-поиска не меняют предикатов допуска: NaN/отрицательная
масса, выход за покрытие или разрыв PVTO всё равно отклоняют пакет.
При непрерывном PVTO используются те же `rtol=1e-7`, `atol=1e-10`.
`torch.no_grad` исключает создание ненужного графа входной проверки;
граф физического интеграла и его чувствительностей не меняется.

[Парное сравнение старого и нового допуска при одном ядре труб](../benchmarks/reports/surface_batch_admission/README.md).

## PVTO без массива всех таблиц по точкам

`PackedPVTO` один раз для пакета труб упаковывает неодинаковые оси давления
с заполнением и хранит реальные длины строк. Для каждого потока выбираются
две соседние Rs-таблицы; `searchsorted` и `gather` работают только с ними.
Порядок арифметики линейной интерполяции и правило правой стороны в узле
совпадают со скалярным эталоном. Первая и вторая производные проверены
на неодинаковых осях и точных PVT-узлах. Глобального кэша нет: упаковка
живёт в `PipeBatch` и создаётся вместе с ним для устройства модели.

Убран временный массив `points × all_Rs_tables` при вычислении Bo и mu_o.
Сетка квадратуры теперь использует общую PVT-ось и узлы только двух
выбранных Rs-таблиц каждого потока. Максимальная длина этих выбранных
осей, а также упаковка свойств по всем таблицам ещё влияют на память.
Входной continuity-check использует отдельный малый пакет значений в
точке насыщения, а не квадратурную сетку.
[Измерения полного FIM и синтетического ядра](../benchmarks/reports/surface_pvto_selection/README.md).

## Сетка по выбранным таблицам

`PipePressureGrid` строит наборы узлов соседних пар PVTO из проверенного
PVT-снимка один раз; таблица осей загружается на устройство одним пакетом.
Кэш принадлежит самому экземпляру свойств, не глобальному процессу.
`BlackOilMixture.to()` создаёт новый независимый снимок и кэш для него.
Переключение пары по составу выполняется тензорно, без чтения номеров
таблиц на host. Внутренний PVT-снимок считается неизменяемым; новую PVT
следует задавать новым экземпляром модели.

Общая ось давления, оба выбранных набора PVTO-узлов и подвижная точка
насыщения сохраняются. Удаляются только узлы таблиц, не участвующих в
свойствах данного потока. Поэтому сохраняются изломы выбранных Bo/mu_o,
а фазовая граница продолжает входить в дифференцируемое разбиение.
Ненулевые интервалы после clipping уплотняются в плане квадратуры;
нулевые сохраняют одну оценку в совпавшей точке для корректных
первых/вторых производных. Полная Gauss-сетка на них не вычисляется.

При одинаковых осях возвращается прежний набор узлов без выбора пары.
Для богатой PVTO-модели компактная сетка допускается и у одиночного
коллектора; обычные одиночные трубы с одинаковыми осями сохраняют
скалярный путь. Условия приёма и явный скалярный повтор не ослабляются.
[Полный FIM с 65 таблицами и обычный контроль](../benchmarks/reports/surface_stream_grid/README.md).

## Уплотнение Gauss-точек без потери граничных производных

`CompactQuadraturePlan` выбирает строго положительные интервалы без
epsilon-отсечения: любой представимый ненулевой интервал сохраняется.
План строится один раз для пробного давления и используется всеми
порядками адаптивной квадратуры. Одно управляющее чтение максимального
числа активных интервалов на пакет задаёт размер тензоров; дополнительных
чтений для каждой трубы или каждого порядка Gauss нет. Это новая
планировочная синхронизация: GPU-выигрыш требует отдельного замера.

Просто удалять интервал нулевой длины нельзя: совпавшие численно концы
могут иметь разные производные, например при совпадении bubble point
с портом трубы. Его вклад в значение нулевой, но вклад в Jacobian
может быть ненулевым. Нулевой half-width остаётся в AD-графе, а
подынтегральная функция оценивается в совпавшей средней точке с суммой
Gauss-весов. Это сохраняет проверенные первые и вторые производные;
эквивалентность производных третьего порядка и выше не заявляется.

Обычные нулевые интервалы, у которых оба конца происходят от одного
предела, отменяются в AD. Ненулевые интервалы и совпавшие точки проходят
одним общим вызовом свойств. Интервалы разных строк дополняются до
максимального активного числа внутри пакета; это не полное устранение
любых padding-точек. PVT-границы, фазовый переход, choking, конечность,
механический баланс и допуски квадратуры остаются прежними.
[Полный FIM, число реальных вычислений свойств и ограничения](../benchmarks/reports/surface_compact_quadrature/README.md).

Оценка `batch * intervals * 256` задаёт исходную Gauss-сетку.
Уплотнённый вызов содержит `batch * (max_active * order + intervals)`
точек, когда есть совпавшие интервалы; добавка midpoint-точек должна
учитываться в ресурсном замере. При почти заполненной очень длинной
сетке уменьшение числа точек не гарантируется. Общий лимит памяти
autograd/процесса этой оценкой не задаётся.

## Общий поиск давления для столбцов свойств

`PressureLookup` сохраняет индексы, delta и span только для текущего
давления и текущей оси. Rs/Bo/Bw/Bg/вязкости разделяют один поиск общей
PVT-оси; Bo и mu_o каждой выбранной PVTO-таблицы разделяют свой поиск.
Порядок `lo + delta * (hi-lo) / span` сохранён. Индексы и граф давления
не кэшируются между пробными давлениями. Новых host-read или физических
настроек эта оптимизация не добавляет.

`PackedPVTO.prepare_lookup(pressure, indices)` создаёт контекст текущей
оси. `interpolate(..., lookup=...)` использует его для нужного столбца;
прежний вызов отдельного столбца без контекста сохраняется. Контекст
внутренний и должен соответствовать тому же давлению и индексам таблиц.
Проверены скалярные/пакетные формы, правые стороны узлов и первые/вторые
производные. [Парные FIM-замеры и определение метрики памяти](../benchmarks/reports/surface_shared_lookup/README.md).
