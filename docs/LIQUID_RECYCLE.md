# Регулируемая рециркуляция жидкостной станции

`RecyclingLiquidStation` добавляет контур минимального расхода к
[защищённой жидкостной станции](LIQUID_PROTECTION.md). Жидкость действительно
возвращается через отдельную ветвь от нагнетательного коллектора к всасыванию.
Контроллер не добавляет источников и не подменяет расход насоса уставкой.

## Гидравлика и движение клапана

В `LiquidTransientNetwork.actuated_valves` существующему открытому
`ThrottleValve` назначается `ConnectionActuator`. Фактическое положение
сохраняется в `LiquidTransientState.actuator_positions`. `valve_openings`
для этих клапанов задаёт **команду**, а не мгновенное положение. Остальные
обычные клапаны сохраняют прежнее мгновенное управление. Предохранительный
клапан с `LiquidRelief` нельзя одновременно назначить приводным.

Привод учитывает разные скорости открытия/закрытия, апериодическое
запаздывание и ограничение перемещения за подшаг. `actuator_modes` задаёт
`normal`, `stuck` или `fail_safe`. При отказе fail_safe целью становится
`fail_position`; мгновенного скачка положения нет. При заклинивании сохраняется
фактическое положение. Режимы отказа задаются на период, не защёлкиваются.

Гидравлика использует положение в середине физического подшага, запас
положения обновляется в конце. При двух полушагах второй начинается с
конечного положения первого; отвергнутые попытки не перемещают привод.
Точное автономное решение движения используется также при локализации
остановки вала. Механическая работа самого штока и электричество привода
клапана не моделируются.

Для приводных клапанов уравнение записано в обратной форме того же закона:

```text
Q = Cd A opening sign(dp) sqrt(2 |dp| / rho_ref)
```

Для обратного клапана используется положительная часть dp. Такая запись
устраняет деление на opening² при почти закрытом клапане. Экспоненциальное
приближение к седлу не обрезается произвольным минимальным открытием.
Работа `dp*Q` входит в диссипацию, расход — в узловые балансы. Приводная
ветвь остаётся безынерционной; для существенной инерции возвратной трубы
нужны отдельные инерционные ветви и конечные объёмы. Текущий recycle-контур
проверяет непосредственное соединение общих нагнетания и всасывания насосов.

## Контуры и приоритеты

`LiquidRecycleLoop` содержит имя, возвратный клапан, непересекающийся список
параллельных насосов, PID с выходом [0,1] и положительным направлением,
`minimum_flow_m3_s`, `min_speed_ratio` (0.6), `startup_opening` (1) и
`inactive_opening` (0). Одна ветвь не может принадлежать двум контурам.

На собственной постоянной шкале времени контур измеряет расход каждого
выбранного доступного насоса с достаточной скоростью. Обратная связь —
минимум этих расходов. При дефиците открывается реальный байпас. Во время
пуска до достижения скорости используется startup_opening; при отсутствии
разрешённых агрегатов — inactive_opening. В auto после ручного режима первый
отсчёт PID обеспечивает безударный переход. Запреты и выбор агрегатов,
изменившиеся внутри нижнего контура, становятся видимыми recycle-регулятору
на его следующем отсчёте; останов приводов защитами не ждёт этого отсчёта.

Защита интегратора использует **фактическое положение**, включая запаздывание,
ограничение скорости и отказ. Ограниченный клапан не гарантирует минимальный
расход: дефицит выводится в `flow_deficit_m3_s`, а существующие защиты малого
расхода могут отключить привод. Рециркуляция не снимает операторский trip,
внешнюю недоступность или защёлку защиты.

`recycle_mode` задаёт auto, manual или off. Для manual необходимы
`recycle_openings` всех контуров. Ручное открытие допустимо и при остановленных
двигателях; `off` задаёт inactive_opening. Прямой `valve_openings` для клапана,
принадлежащего recycle-контуру, отвергается как конфликт владельцев управления.
Fail-safe привод имеет физический приоритет над командой PID/manual/off.

Диспетчеризация насосов использует явно заданный
`ControlledLiquidStation.planning_valve_openings={"recycle": 0}`. Это номинальное
предположение только для стационарного выбора агрегатов. Фактическое давление
и электрические ограничения берутся из динамики. Изменения команды recycle
не запускают дорогой перебор конфигураций на каждом отсчёте. Оптимальность
энергопотребления с учётом изменяющегося байпаса здесь не заявляется.

## Расписание, учёт и продолжение

Пример: `configs/surface_recycling_liquid.json`. Конфигурация содержит
`system.protected`, `system.loops` и `system.control_interval_s` (0.05).
`initial.protected_initial` передаётся существующей защищённой станции.
Периоды поддерживают её команды плюс recycle_mode, recycle_openings,
actuator_modes и max_recycle_samples. Бюджеты отсчётов/подшагов действуют на
весь отчёт, а не заново на каждое внутреннее окно.

```bash
python scripts/run_recycling_liquid.py configs/surface_recycling_liquid.json \
  --output results/recycle/full.json
python scripts/run_recycling_liquid.py configs/surface_recycling_liquid.json \
  --stop-after 2 --output results/recycle/partial.json
python scripts/run_recycling_liquid.py configs/surface_recycling_liquid.json \
  --checkpoint results/recycle/partial.json --output results/recycle/resumed.json
python scripts/check_liquid_recycle.py --trajectory results/recycle/full.json \
  --output results/recycle/validation.json
```

`recycled_volume_m3` интегрирует возвратный расход отдельно от экспортного.
Граничный баланс учитывает суммарный приток насосов и возврат в резервуар:
при закрытом экспорте установившаяся рециркуляция не является добычей.

Checkpoint сохраняет физические запасы, фактические положения, все PID,
три независимых шкалы времени и защёлки. Продолжение проверяет исходники,
конфигурацию, контрольную сумму и повторно рассчитывает сохранённую историю.
Обновление исходников делает старые source-bound checkpoints несовместимыми.
JSON записывается атомарно. Replay имеет отдельную стоимость при продолжении.

## Область подтверждения

Независимый аналитический эталон: истечение из упругой ёмкости через клапан
с известной экспоненциальной траекторией. Дополнительно проверяются точное
стационарное замкнутое обращение, заклинивание с реальным trip, ограничения
перемещения, почти закрытый клапан и продолжение между цифровыми отсчётами.

Это горизонтальная слабосжимаемая однофазная изотермическая жидкость, прямые
насосные карты и PyTorch float64 с явным CPU/CUDA. В исходном классе нагрев отсутствует;
он доступен в [калорическом расширении](THERMAL_LIQUID.md).
Кавитация, четырёхквадрантные режимы, многокомпонентный перенос, PR-машины,
единое сопряжение этой динамики с FIM остаются отдельными задачами.
Паспортные данные не предоставлены: синтетические проверки не являются
калибровкой оборудования или доказательством превосходства над коммерческим ПО.

Тепловое накопление, конечный всасывающий резервуар, стенки и температурные
защиты теперь доступны в отдельном [калорическом расширении](THERMAL_LIQUID.md).
Они не меняют область применимости исходного изотермического класса.

## Численное устройство

Текущий путь динамической жидкостной модели использует PyTorch float64;
CPU/CUDA задаются явно. `scipy_reference` сохраняет прежний CPU-эталон.
Границы переноса и оставшийся CPU-обмен описаны в
[PyTorch в наземной динамике](PYTORCH_SURFACE.md).
