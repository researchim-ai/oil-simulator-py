# Тепловая подготовка явной PR-смеси

Этот модуль объединяет [термодинамику смеси](THERMODYNAMICS.md) в ациклическую
схему установившихся операций. Он использует те же PT/PH/PS и численную проверку
устойчивости, что тепловой сброс давления и HEM-сопло. Стандартные black-oil
потоки не преобразуются в компонентный состав автоматически.

## Поток и соглашения

`ThermalStream` содержит `component_molar_rates_mol_s`, `pressure_pa`,
`molar_enthalpy_j_mol` и `model_id`. Энергетический поток равен суммарному
молярному расходу, умноженному на молярную энтальпию. Массы компонентов
получаются умножением молярных расходов на индивидуальные молярные массы.
Суммировать фазовые объёмы при разных условиях вместо компонентных масс нельзя.

Отпечаток `model_id` включает порядок и параметры компонентов, kij, калорику
и опорное состояние. Перед операцией он сверяется с моделью. Поток из другого
EOS-пакета или с переставленными компонентами отклоняется, даже если длины
массивов совпадают. Сырые энтальпии разных пакетов не смешиваются.

Для ненулевого потока все включённые компоненты должны иметь положительные
расходы. Отсутствующий компонент исключается из модели, а не заменяется
скрытым следовым количеством. Полностью нулевой поток допускается;
`state(fluid)` возвращает `None`. Давление в таком объекте — объявленный
параметр схемы, не расчёт физического давления остановленного аппарата.

```python
from surface import ThermalStream, MixtureHeatExchanger

stream = ThermalStream.from_pt(
    fluid, pressure_pa=3e6, temperature_k=260,
    molar_rate_mol_s=10, mole_fractions=[0.5, 0.5],
)
result = MixtureHeatExchanger(
    "cooler", outlet_temperature_k=220,
    utility_temperature_k=180, pressure_drop_pa=1e5,
).run(stream, fluid)
```

## Операции

### Смешение и разделение расхода

`mix_thermal_streams(streams, fluid)` суммирует компонентные расходы и
энтальпийные потоки. Температура смеси получается PH-flash; она не усредняется
арифметически. Требуются одинаковые давления — понижение давления перед
смешением должно быть отдельной явной операцией. Положительная генерация
энтропии при смешении учитывается.

`stream.split(fraction)` создаёт два потока одинакового состава и удельной
энтальпии с указанным разделением расходов. Это не фазовая сепарация.
Повторное использование одного расхода без явного split запрещено в схеме.

### Нагрев и охлаждение

`MixtureHeatExchanger` задаёт выходную температуру, постоянную температуру
внешнего теплового резервуара и необязательную потерю давления. Выходное
равновесие может содержать конденсацию или испарение. Теплота:

```
Q = H_out - H_in
S_gen = S_out - S_in - Q / T_utility
```

Q положительна при подводе тепла к рабочему потоку. Проверяются направление
теплообмена относительно конечных температур, неотрицательная генерация
энтропии и `max_abs_duty_w`, если предел задан. Невыполнимый режим вызывает
ошибку, а не подменяется недостигнутой уставкой. Температурная область EOS
проверяется и при остановке.

Это модель заданной температуры с энергетическим балансом, не расчёт площади,
UA, внутреннего профиля температур или конечного расхода охлаждающей воды.
Проверка конечных температур не заменяет pinch-анализ реального теплообменника.

### Повышение давления

`MixturePressureRaiser` — адиабатическая термодинамическая модель работы:

```
h_2s = flash_PS(P_out, s_in, z).h
h_out = h_in + (h_2s - h_in) / eta_is
W_shaft = N_dot * (h_out - h_in)
```

Вход, изоэнтропийный конечный и фактический конечный режимы должны быть
однофазными. Двухфазные состояния отклоняются. Эффективность задаётся явно
в диапазоне (0,1]; ограничения `max_power_w` и `max_outlet_temperature_k`
необязательны. W положительна при работе над потоком. Это мощность в рабочий
флюид, не электрическая мощность двигателя с механическими потерями.

Соглашения соответствуют [isentropic pressure changer в IDAES](https://idaes-pse.readthedocs.io/en/stable/reference_guides/model_libraries/generic/unit_models/pressure_changer.html).
Модель не подменяет характеристику реального компрессора/насоса: нет карты,
помпажа, NPSH, скоростей вращения, промежуточного пути в машине или защит.
Пригодность конкретного аппарата требует отдельной проверки.

### Сброс давления и сепаратор

`let_down_thermal_stream` сохраняет компонентные расходы и энтальпию;
температура после снижения давления получается PH-flash. Расход здесь задан,
пропускная способность арматуры не определяется.

`MixtureFlashSeparator` выполняет адиабатический PH-flash при заданном
давлении и распределяет расходы по равновесным составам фаз. В двухфазном
режиме первый выход — жидкость, второй — пар. Массовая доля не подменяется
молярной; фазовые энтальпии входят в общий энергетический баланс.

Если равновесие однофазное, без `single_phase_outlet` расчёт отклоняется.
Оператор должен явно выбрать порт 0 или 1; второй порт получает нулевой поток.
Метаданные `phase_roles` в этом случае — `single`/`absent`, а не выдуманная
классификация по плотности. При полном отсутствии расхода оба порта пусты.

Это идеальный равновесный сосуд: нет уноса, капель, времени пребывания,
запасов, уровней и геометрического sizing. Описание общего подхода к
[фазовому разделению и балансу аппарата](https://idaes-pse.readthedocs.io/en/stable/reference_guides/model_libraries/generic/unit_models/flash.html).

## Схема и общий баланс

`run_thermal_flowsheet(fluid, feeds, units)` выполняет операции в порядке
списка. Каждая операция содержит `name`, `type`, `inputs`, `outputs`,
`parameters`. Ссылки на будущие или уже потреблённые потоки, повторные имена,
неизвестные поля и перезапись существующего потока отклоняются.
Все непотреблённые потоки считаются продуктами схемы.

Проверяются балансы каждого аппарата и границы всей схемы:

```
component_in = component_products
H_products - H_feeds = sum(Q) + sum(W_shaft)
S_products - S_feeds - sum(Q_i / T_utility_i) >= 0
```

Энтропийный перенос каждого источника тепла суммируется отдельно. Нулевая
суммарная теплота не означает нулевой перенос энтропии между резервуарами.
Численные остатки выводятся явно; составы и энтальпии не корректируются
задним числом ради закрытия баланса.

Схема — последовательное вычисление DAG с заданными давлениями/подачами,
не решение давления сети, рециклов или связанного ограничения дебитов пласта.
HEM-сопло пока не включено как расходозадающая связь этой схемы: для этого
нужно согласовать давления и пропускную способность, а не назначить оба независимо.

## Расписание и перезапуск

`run_thermal_schedule` принимает периоды с `duration_s` и полным набором `feeds`.
Каждый период — самостоятельный установившийся режим с необязательными
командами аппаратов и общими ресурсами, описанными ниже. Накапливаются моли
продуктов по компонентам, теплота и работа. Интервал без подачи даёт нулевые
накопления, без фиктивных температур выходов.

JSON checkpoint хранит индекс периода, время, принятые результаты и накопления.
Проверяются контрольная сумма, отпечатки модели/схемы/расписания/реализации,
согласование времени и накоплений с сохранёнными записями. Изменение рецепта
после сохранения отклоняется. Контрольная сумма предназначена для обнаружения
повреждения данных, не является цифровой подписью.

Расчёт меняет только локальное состояние: ошибка не повреждает переданный
checkpoint. CLI записывает результат через временный файл и атомарную замену;
предыдущий файл сохраняется при отказе расчёта. Это транзакция одного вызова,
не автоматическое сохранение каждого внутреннего периода при аварии процесса.
Для промежуточного сохранения применяется `--stop-after`.

```bash
python scripts/run_surface_process.py configs/surface_thermal_process.json --output /tmp/thermal.json --stop-after 1
python scripts/run_surface_process.py configs/surface_thermal_process.json --checkpoint /tmp/thermal.json --output /tmp/thermal.json
```

Использованы общие канонические контрольные суммы существующего модуля
расписаний наземной части; состав и энергетический базис нового режима
сохраняются отдельно от black-oil.

## Ограничения и проверка

CPU reference, постоянные kij и идеальные Cp, только VLE до двух фаз.
Нет водной фазы, экспериментально откалиброванных свойств нефти,
динамических запасов/уровней, рециклов, общей сети давлений, подключения
теплового контура к FIM или GPU-пакетирования.

Проверки включают независимый идеальногазовый предел работы и теплообмена,
конденсацию и фазовое разделение, общий компонентный/энергетический баланс,
запрет несовместимых моделей, ограничения оборудования, остановку,
JSON-перезапуск и сохранность checkpoint при отказе.
Численные протоколы находятся в `reports/validation`, журналы — в `results`.

## Управление по периодам и общие ресурсы

Необязательный `unit_controls` периода задаёт изменения параметров аппаратов
по их именам. Меняются только физические уставки, КПД, пределы и доли split;
топология и подключения потоков неизменны. Каждый период начинает с базового
`units`, а не наследует неуказанные команды предыдущего периода. Уставки
проверяются до расчёта, включая интервалы без подачи.

`ThermalResourceLimits` задаёт `max_shaft_power_w`, `max_heating_w`,
`max_cooling_w`. Пропущенный/null предел не ограничивает ресурс, ноль означает
отсутствие доступного ресурса. Нагрев и охлаждение суммируются **раздельно по
аппаратам**: малая результирующая Q не означает малую нагрузку котельной/охлаждения.
Мощность — работа в рабочий флюид, без модели электропривода.

При включённом контроле все запрошенные подачи уменьшаются общим множителем.
Для поддержанных аппаратов при фиксированных P/T/eta и долях split составы
и удельные свойства не зависят от этого множителя; Q и W пропорциональны расходу.
Это позволяет вычислить допустимую долю по отношениям пределов к потенциальным
нагрузкам, затем **заново решить** схему с исходными ограничениями аппаратов.
При численном отказе или нарушении фазовой области ошибка распространяется;
она не интерпретируется как ограниченная производительность.

Потенциальный расчёт временно снимает только абсолютные пределы мощности/
тепловой нагрузки. Предел температуры, область фаз, направление теплообмена
и все проверки баланса остаются. Последний расчёт использует исходные пределы;
небольшой внутренний запас округления множителя предотвращает превышение
из-за перестановки операций с плавающей точкой. Минимальные рабочие расходы,
карты оборудования и зависящие от расхода давления в этой модели отсутствуют.
На них аналитическое масштабирование автоматически не распространяется.

В отчёте `capacity_control` сохраняются допустимая доля, потенциальные и
принятые нагрузки, активные ограничения и непринятые компонентные расходы.
Checkpoint раздельно накапливает `requested_component_moles`,
`product_component_moles`, `unprocessed_component_moles` и проверяет:

```
requested_components = product_components + unprocessed_components
```

Непринятая подача не считается продукцией и не исчезает из учёта. Это результат
самостоятельного расчёта наземной площадки; управление дебитами пластового FIM
данным контроллером пока не реализовано.

Пределы по умолчанию задаются в корневом `resource_limits`. Необязательный
блок периода полностью заменяет корневой на этот период; пропущенные в нём
пределы становятся неограниченными. Пустой блок включает контроль абсолютных
лимитов аппаратов без общих ограничений. Без блока сохранён строгий режим:
превышение лимита аппарата вызывает отказ, без автоматического снижения подачи.

```bash
python scripts/run_surface_process.py configs/surface_thermal_process_controlled.json --output /tmp/controlled.json
```

Команды и ресурсы входят в отпечаток checkpoint и сохраняются в записях периодов.
Изменённая схема/реализация не возобновляет старый checkpoint молча.


Для отдельного жёсткого аппарата реализован [динамический сосуд](DYNAMIC_VESSEL.md)
с компонентными запасами и внутренней энергией. Это отдельный контрольный
объём; DAG выше остаётся установившимся, динамическая сеть из него не выводится автоматически.
