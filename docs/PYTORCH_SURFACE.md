# PyTorch в динамической жидкостной сети

Гидравлика `LiquidTransientNetwork` и калорический перенос `LiquidHeatNetwork`
используют `backend="torch"` по умолчанию. Числа — `torch.float64`;
геометрия и численные операторы создаются на явно выбранном устройстве.
Это относится к горизонтальной слабосжимаемой однофазной модели, а не означает
готовность многофазной тепловой наземной сети или перенос всех старых классов.

## Выбор устройства

По умолчанию `device="cpu"`: библиотека не выбирает произвольно одну из
доступных карт, на которой может идти другой расчёт. Для CUDA задайте
`"device": "cuda:0"` в блоке `physics`, содержащем `network` и
`storage_volumes_m3`. Тепловой блок наследует устройство физики.
Пять `scripts/run_*liquid*.py` также поддерживают `--device` и `--backend`.

Пример выбора конкретной карты по UUID:

```bash
CUDA_VISIBLE_DEVICES=GPU-9ade3f1f-7ead-7504-f762-07be60234d31 \
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/run_thermal_liquid.py configs/surface_thermal_liquid.json \
  --device cuda:0 --output results/thermal_cuda.json
```

UUID в примере относится к проверенной RTX 3090 этой машины. На другой
машине используйте свой UUID. После `CUDA_VISIBLE_DEVICES` выбранная карта
видна программе как `cuda:0`. Недоступная CUDA вызывает ошибку: скрытого
перехода на CPU нет. `scipy_reference` — явный режим только для CPU,
сохраняющий прежние уравнения как контроль реализации.

## Что считает Torch

* Совместная система давлений, инерционных расходов труб и скоростей валов.
* Фрикционные потери, переход ламинарного/турбулентного закона,
  табличные карты, обратные клапаны, регулируемые и предохранительные клапаны.
* Момент, электрические ограничения, рекуперация, NPSH и ограничения карт.
* Предварительные стационарные решения для диспетчеризации новой динамической
  станции; показания расхода и NPSH её датчиков.
* Перенос энтальпии при обоих направлениях течения, меняющиеся массы,
  конечные резервуары, стенки, тепловые источники и балансы энергии.

Ньютон использует точные производные уравнений через `torch.func.jacfwd`.
Для систем выше установленного малого предела применяются раскраска
структуры Якобиана и матрично-свободный GMRES с разреженным оператором.
Автоматического превращения большой матрицы в плотную нет. Неудачная
СЛАУ/нелинейная система не считается принятой физикой.

На CUDA повторяемые группы итераций гидравлики захватываются в CUDA Graph;
варианты line search считаются совместно. Между группами требуется
масштабированная невязка не более 2e-11.
Между группами читается скалярный статус, матрицы и векторы Ньютона остаются
на устройстве. Малый тепловой оператор решается Torch LU; большой —
консервативной итерацией при ограничении позитивности с обязательной
проверкой невязки и энергии. Оператор и диагональ собираются тензорами. На CUDA локальные суммы
разреженного оператора группируются по числу элементов в строке, чтобы
не использовать тяжёлую универсальную редукцию для строк из 1–2 элементов.

Это ещё не квалификация разреженного гидравлического решателя на сотнях
тысяч наземных неизвестных: размеры, нелинейная обусловленность и
предобуславливание требуют отдельных крупных связанных задач.

## Обмен CPU–GPU

Обычный API станции сохраняет словари, JSON и историю каждого принятого
физического подшага. Его адаптер упаковывает входы одного решения и
скачивает результаты одним пакетом; нет пересылки матрицы на каждой
итерации. Однако расписание, PID, дискретная диспетчеризация, локализация
событий и сериализация пока выполняются на CPU. Для этого API нельзя
утверждать, что между подшагами отсутствует обмен полями.

`TorchHeatInterval` предоставляет отдельный режим для **теплового интервала
с предписанными гидравлическими расходами и мощностями**. На устройстве
остаются температуры, массы, полный шаг/два полушага и балансы всех подшагов.
На CUDA граф повторяется без чтения полей CPU; одна проверка статуса
принимает или отклоняет весь интервал. При отказе входное состояние не
изменяется. Число подшагов задаётся явно; при нарушении временной точности,
позитивности, температурной области или энергии интервал нужно повторить
с меньшим шагом. Это транспортный интегратор, не замена гидравлического
решения, защит, остановок или регуляторов станции.

```python
from surface import TorchHeatEquations, TorchHeatInterval, TorchHeatState

kernel = TorchHeatEquations(heat_model, device="cuda:0")
# T: все температуры жидкости, затем стенок; M: массы жидких объёмов.
state = TorchHeatState(kernel.tensor(T), kernel.tensor(M))
result = TorchHeatInterval(kernel).advance(
    state, end_mass=kernel.tensor(M_end),
    flows=kernel.tensor(branch_volume_rates),
    heat_j=kernel.tensor(branch_heat_for_whole_interval),
    duration_s=duration, substeps=number_of_steps,
)
# result.state и result.audit остаются тензорами CUDA.
```

Порядок неизвестных задают `heat_model.names`, `heat_model.wall_names`;
порядок ветвей — `kernel.branch_names`. Для построения `heat_j` из механических
потерь предусмотрен `kernel.heat_vector`. Входы должны быть float64 на
том же устройстве, с точными размерами. Интервалы требуют постоянных расходов,
мощностей и граничных температур; массы между концами интерполируются
линейно, как внутри одного гидравлического отчётного подшага.

## Воспроизводимость и проверки

Checkpoint включает версии Torch/CUDA-сборки, настройку детерминированных
алгоритмов, устройство в модели и хеши новых численных исходников.
Checkpoint до миграции нужно пересчитать. Перенос checkpoint между CPU и
CUDA с изменением модели не объявляется побитно совместимым.

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python -m pytest -q tests/test_surface_torch.py
python scripts/benchmark_torch_surface.py --device cpu --output results/torch_cpu.json
CUDA_VISIBLE_DEVICES=<UUID> python scripts/benchmark_torch_surface.py \
  --device cuda:0 --output results/torch_cuda.json
```

Тесты сопоставляют Torch CPU/CUDA с явным SciPy-эталоном, проверяют
повторный CUDA Graph с изменёнными командами, разреженный Якобиан и физическую акустическую моду на 161 неизвестной,
энергию, отклонение некорректного интервала и отсутствие вызовов
SciPy-решателей при автоматической работе станции. Тепловой бенчмарк
сверяется с независимой аналитической цепочкой перемешиваемых объёмов.
Это заданные расходы, **не** бенчмарк большого связанного месторождения.
Время GPU включает синхронизацию; для тепла также включён захват графа.
Начальная сборка модели и первичная загрузка выделены в `setup_seconds_including_initial_upload`.
В размерном тесте фиксированы 64 подшага и число Куранта; длительность
интервала равна 16/N секунд и уменьшается при росте числа ячеек N.
Этот тест измеряет стоимость работы с полями, не скорость прохождения
одинакового физического времени на разных сетках.
Малая сеть может работать на CPU быстрее GPU: перенос архитектуры сам по
себе не является доказательством ускорения.

Остальные исторические реализации PR/PVT, газовой сети и стационарного
оборудования этим переносом не переписываются. Пластовый FIM этим блоком
не изменяется. Производительность Norne нужно проверять отдельно после
согласованного сопряжения, а не выводить из теплового теста.
