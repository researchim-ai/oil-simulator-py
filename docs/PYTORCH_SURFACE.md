# PyTorch в динамической жидкостной сети

Гидравлика `LiquidTransientNetwork` и калорический перенос `LiquidHeatNetwork`
используют `backend="torch"` по умолчанию. Числа — `torch.float64`;
геометрия и численные операторы создаются на явно выбранном устройстве.
Это относится к горизонтальной слабосжимаемой однофазной модели, а не означает
готовность многофазной тепловой наземной сети или перенос всех старых классов.

## Выбор устройства

По умолчанию `device="cpu"`: библиотека не выбирает произвольно одну из
доступных карт, на которой может идти другой расчёт. Для CUDA задайте
`"device": "cuda:0"` в блоке `physics`, содержащем `network` и
`storage_volumes_m3`. Тепловой блок наследует устройство физики.
Пять `scripts/run_*liquid*.py` также поддерживают `--device` и `--backend`.

Пример выбора конкретной карты по UUID:

```bash
CUDA_VISIBLE_DEVICES=GPU-9ade3f1f-7ead-7504-f762-07be60234d31 \
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/run_thermal_liquid.py configs/surface_thermal_liquid.json \
  --device cuda:0 --output results/thermal_cuda.json
```

UUID в примере относится к проверенной RTX 3090 этой машины. На другой
машине используйте свой UUID. После `CUDA_VISIBLE_DEVICES` выбранная карта
видна программе как `cuda:0`. Недоступная CUDA вызывает ошибку: скрытого
перехода на CPU нет. `scipy_reference` — явный режим только для CPU,
сохраняющий прежние уравнения как контроль реализации.

## Что считает Torch

* Совместная система давлений, инерционных расходов труб и скоростей валов.
* Фрикционные потери, переход ламинарного/турбулентного закона,
  табличные карты, обратные клапаны, регулируемые и предохранительные клапаны.
* Момент, электрические ограничения, рекуперация, NPSH и ограничения карт.
* Предварительные стационарные решения для диспетчеризации новой динамической
  станции; показания расхода и NPSH её датчиков.
* Перенос энтальпии при обоих направлениях течения, меняющиеся массы,
  конечные резервуары, стенки, тепловые источники и балансы энергии.

Ньютон использует точные производные уравнений через `torch.func.jacfwd`.
Для систем выше установленного малого предела применяются раскраска
структуры Якобиана и матрично-свободный GMRES с разреженным оператором.
Автоматического превращения большой матрицы в плотную нет. Неудачная
СЛАУ/нелинейная система не считается принятой физикой.

На CUDA повторяемые группы итераций гидравлики захватываются в CUDA Graph;
варианты line search считаются совместно. Между группами требуется
масштабированная невязка не более 2e-11.
Между группами читается скалярный статус, матрицы и векторы Ньютона остаются
на устройстве. Малый тепловой оператор решается Torch LU; большой —
консервативной итерацией при ограничении позитивности с обязательной
проверкой невязки и энергии. Оператор и диагональ собираются тензорами. На CUDA локальные суммы
разреженного оператора группируются по числу элементов в строке, чтобы
не использовать тяжёлую универсальную редукцию для строк из 1–2 элементов.

Это ещё не квалификация разреженного гидравлического решателя на сотнях
тысяч наземных неизвестных: размеры, нелинейная обусловленность и
предобуславливание требуют отдельных крупных связанных задач.

## Обмен CPU–GPU

Обычный API станции сохраняет словари, JSON и историю каждого принятого
физического подшага. Его адаптер упаковывает входы одного решения и
скачивает результаты одним пакетом; нет пересылки матрицы на каждой
итерации. Однако расписание, PID, дискретная диспетчеризация, локализация
событий и сериализация пока выполняются на CPU. Для этого API нельзя
утверждать, что между подшагами отсутствует обмен полями.

`TorchHeatInterval` предоставляет отдельный режим для **теплового интервала
с предписанными гидравлическими расходами и мощностями**. На устройстве
остаются температуры, массы, полный шаг/два полушага и балансы всех подшагов.
На CUDA граф повторяется без чтения полей CPU; одна проверка статуса
принимает или отклоняет весь интервал. При отказе входное состояние не
изменяется. Число подшагов задаётся явно; при нарушении временной точности,
позитивности, температурной области или энергии интервал нужно повторить
с меньшим шагом. Это транспортный интегратор, не замена гидравлического
решения, защит, остановок или регуляторов станции.

```python
from surface import TorchHeatEquations, TorchHeatInterval, TorchHeatState

kernel = TorchHeatEquations(heat_model, device="cuda:0")
# T: все температуры жидкости, затем стенок; M: массы жидких объёмов.
state = TorchHeatState(kernel.tensor(T), kernel.tensor(M))
result = TorchHeatInterval(kernel).advance(
    state, end_mass=kernel.tensor(M_end),
    flows=kernel.tensor(branch_volume_rates),
    heat_j=kernel.tensor(branch_heat_for_whole_interval),
    duration_s=duration, substeps=number_of_steps,
)
# result.state и result.audit остаются тензорами CUDA.
```

Порядок неизвестных задают `heat_model.names`, `heat_model.wall_names`;
порядок ветвей — `kernel.branch_names`. Для построения `heat_j` из механических
потерь предусмотрен `kernel.heat_vector`. Входы должны быть float64 на
том же устройстве, с точными размерами. Интервалы требуют постоянных расходов,
мощностей и граничных температур; массы между концами интерполируются
линейно, как внутри одного гидравлического отчётного подшага.

## Воспроизводимость и проверки

Checkpoint включает версии Torch/CUDA-сборки, настройку детерминированных
алгоритмов, устройство в модели и хеши новых численных исходников.
Checkpoint до миграции нужно пересчитать. Перенос checkpoint между CPU и
CUDA с изменением модели не объявляется побитно совместимым.

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python -m pytest -q tests/test_surface_torch.py
python scripts/benchmark_torch_surface.py --device cpu --output results/torch_cpu.json
CUDA_VISIBLE_DEVICES=<UUID> python scripts/benchmark_torch_surface.py \
  --device cuda:0 --output results/torch_cuda.json
```

Тесты сопоставляют Torch CPU/CUDA с явным SciPy-эталоном, проверяют
повторный CUDA Graph с изменёнными командами, разреженный Якобиан и физическую акустическую моду на 161 неизвестной,
энергию, отклонение некорректного интервала и отсутствие вызовов
SciPy-решателей при автоматической работе станции. Тепловой бенчмарк
сверяется с независимой аналитической цепочкой перемешиваемых объёмов.
Это заданные расходы, **не** бенчмарк большого связанного месторождения.
Время GPU включает синхронизацию; для тепла также включён захват графа.
Начальная сборка модели и первичная загрузка выделены в `setup_seconds_including_initial_upload`.
В размерном тесте фиксированы 64 подшага и число Куранта; длительность
интервала равна 16/N секунд и уменьшается при росте числа ячеек N.
Этот тест измеряет стоимость работы с полями, не скорость прохождения
одинакового физического времени на разных сетках.
Малая сеть может работать на CPU быстрее GPU: перенос архитектуры сам по
себе не является доказательством ускорения.

Остальные исторические реализации PR/PVT, газовой сети и стационарного
оборудования этим переносом не переписываются. Пластовый FIM этим блоком
не изменяется. Производительность Norne нужно проверять отдельно после
согласованного сопряжения, а не выводить из теплового теста.

## Тепловое состояние между отсчётами управления

`ThermalLiquidStation.advance` теперь по умолчанию использует
`thermal_state_transfer="report"`. Температуры жидкости и стенок и массы
остаются на устройстве между гидравлическими подшагами и между отсчётами
температурных защит/PID. В конце каждого окна регуляторы получают только
свои объявленные температуры из принятого состояния. Полное текущее
состояние выгружается в конце отчётного интервала для результата и restart.
Расписание, границы подшагов, дискретный такт, выдержки защит, ограничения
тепловых ресурсов и критерии приёмки не изменены.

Для парной проверки предусмотрены три способа передачи состояния:

- `report` — одно начальное состояние и один итоговый экспорт на весь отчёт;
- `window` — текущее состояние экспортируется между окнами температурного управления;
- `record` — прежний путь с сериализацией после каждого гидравлического подшага.

Это параметр исполнения, не новая физика. Его можно задать в периоде
расписания или через `scripts/run_thermal_liquid.py --thermal-state-transfer`.
При продолжении расписания используйте те же параметры: fingerprint
учитывает периоды и численные исходники, включая модуль сессии.
`scipy_reference` сохраняет прежний CPU-путь, без скрытого выбора Torch/CUDA.

```bash
CUDA_VISIBLE_DEVICES=<UUID> OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/run_thermal_liquid.py configs/surface_thermal_liquid.json \
  --device cuda:0 --thermal-state-transfer report --output results/thermal_report.json
```

Отдельный API для уже принятых гидравлических записей:

```python
session = heat_model.open_session(initial_heat_state,
                                  fluid_sensors=("header",), wall_sensors=("header",))
window = session.advance_records(accepted_hydraulic_records,
                                 ambient_temperatures_k={"header": 295.0})
observations = window["state"]  # Только объявленные датчики, не restart-состояние.
# Следующее окно продолжает те же поля без их выгрузки/загрузки.
window = session.advance_records(next_accepted_records)
final_heat_state = session.close()  # Полное LiquidHeatState для сохранения.
```

Состояние окна принимается только после всех его балансов и проверок.
При отказе можно повторить окно на той же сессии с корректными записями;
курсор сессии и исходное публичное состояние не меняются. `snapshot()`
делает явный полный экспорт без закрытия. После `close()` расчёт и
наблюдение через эту сессию отклоняются. Изменение модели в открытой
сессии также отклоняется. `align_time()` допускает только погрешность
округления конечного времени, а не пропуск непройденного интервала.

Обычный `heat_model.advance_records(..., resident=True)` удерживает поля
только внутри переданного списка и возвращает полное состояние. При
`resident=False` выполняется путь `advance_record` для каждой записи.

### Журнал и счётчики

`store_step_temperatures=True` по-прежнему сохраняет **все** запрошенные
промежуточные температурные поля. Их экспорт нужен для журнала даже в
режиме `report`. Он ограничен порциями около 16 MiB плюс один кадр;
при сборке порции временно нужна дополнительная копия. Скаляры балансов
ограничены заданным бюджетом числа подшагов. Для больших моделей обычно
нужен `heat.store_step_temperatures=false`: балансы и показания регуляторов
сохраняются, температурные кадры каждого подшага не создаются.

`session.transfer_stats()` и результат `advance_records()["transfer_stats"]`
показывают логические пакеты/байты адаптера, отдельно состояние, датчики
и температурный журнал. На CPU это объём сериализации, не PCIe. Начальная
сборка геометрии не входит в счётчики. Скалярные проверки адаптивного шага,
записи балансов и входные гидравлические записи всё ещё обмениваются с CPU.
Число всех пакетов поэтому не обязано уменьшаться вместе с объёмом полей.
Последовательное чередование сессий одной модели не смешивает их счётчики;
для одновременных потоков расчёта нужны отдельные экземпляры модели.

```bash
CUDA_VISIBLE_DEVICES=<UUID> OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/benchmark_heat_state_transfer.py --device cuda:0 \
  --cells 4096 32768 262144 --records 16 --modes record window report \
  --output results/heat_transfer.json

CUDA_VISIBLE_DEVICES=<UUID> OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/benchmark_heat_state_transfer.py --device cuda:0 \
  --config configs/surface_thermal_liquid.json --modes record report \
  --save-runs results/heat_transfer_full --output results/heat_transfer_full.json
```

Первый тест задаёт консервативные расходы и сравнивает точные хеши полей
и каждого баланса при разных способах передачи. Это не решение большой
гидравлической сети. Второй выполняет весь связанный сценарий станции,
с регуляторами, защитами, охлаждением и повторным пуском. Время
синхронизировано с CUDA; setup и прогрев выделены отдельно.

Резидентное механическое состояние реализовано отдельным режимом,
описанным ниже. Перенос не добавляет PR/газовую динамику,
многокомпонентную энергию или новую калибровку свойств.

## Механическое состояние между пробными решениями

`LiquidTransientNetwork.advance` использует
`hydraulic_state_transfer="interval"` для backend Torch. Давления,
инерционные расходы труб и скорости валов продолжаются тензорами между
полным шагом и полушагами, принятыми подшагами и последовательными вызовами
`advance`. Публичный формат состояния и полного журнала сохранён.
Для парной проверки доступен прежний путь `hydraulic_state_transfer="solve"`.
Параметр проходит через контролируемую/защищённую/рециркуляционную/тепловую
станцию и расписания. Все пять CLI жидкостных расписаний поддерживают
`--hydraulic-state-transfer interval|solve`.

На пробном решении CPU получает статусы сходимости, физических ограничений
и балансов. Векторы неизвестных Ньютона и невязки в новом режиме не
выгружаются. Полные данные отчёта материализуются только после временной
приёмки шага. Предохранительный сброс, закрытие обратных клапанов,
ограничения давления/сжимаемости, мощности/скорости,
рекуперация и локализация тормозной остановки сохраняют прежние проверки.
Текущая акустическая модель остаётся горизонтальной; этот перенос не
добавляет геометрические высоты или кавитацию.

Контрольная CPU-копия последних принятых координат позволяет повторно
использовать GPU-состояние после пересоздания публичного состояния из JSON.
Проверяются эффективные float64-биты координат, включая знак нуля, модель
и точное время. Изменённые координаты или время требуют новой загрузки;
изменение модели после создания численного ядра отклоняется. Команды,
граничные значения и положения арматуры обновляются отдельно от этого кэша.
Кэш механического состояния фиксируется только после успешного завершения
и проверки всего публичного интервала. Неудачный интервал его не заменяет.

Постоянные граничные значения и команды повторно используются только при
точном совпадении их входных значений. Вектор фиксированных давлений
создаётся на устройстве; передаются значения граничных узлов. Изменение
шага обновляет скаляр на устройстве, а не создаёт CPU-backed Tensor при
каждом решении. Положения регулируемой арматуры проверяются заново для
каждого полного/половинного/событийного шага.

Тормозная остановка сохраняет поиск корня с прежними допусками времени.
CPU получает индексы кандидатов на остановку и скаляр минимальной
скорости; полного возврата механического состояния для этого не требуется.
Слабый положительный разгон и свободный выбег не обнуляются.

```bash
CUDA_VISIBLE_DEVICES=<UUID> OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/run_thermal_liquid.py configs/surface_thermal_liquid.json \
  --device cuda:0 --hydraulic-state-transfer interval \
  --thermal-state-transfer report --output results/station_resident.json

CUDA_VISIBLE_DEVICES=<UUID> OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/benchmark_liquid_state_transfer.py --device cuda:0 \
  --cells 32 80 256 --intervals 3 --macro-steps 4 \
  --output results/mechanical_transfer_waves.json

CUDA_VISIBLE_DEVICES=<UUID> OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python scripts/benchmark_liquid_state_transfer.py --device cuda:0 \
  --config configs/surface_thermal_liquid.json --modes solve interval \
  --save-runs results/mechanical_transfer_full --output results/mechanical_transfer_full.json
```

Волновой тест решает физическую акустическую задачу и проверяет её
независимую моду; сравниваются все шаги/балансы двух способов исполнения.
JSON показывает, строился ли разреженный Якобиан и сколько цветов
использовано. Он не квалифицирует миллионную связанную наземную модель.
Полный тест сохраняет работу всей станции с прежними тепловыми параметрами.

Счётчики механического адаптера доступны через
`physics._torch_bridge.transfer_stats()` для диагностики. Отдельно видны
загрузка состояния, выгрузка векторов Ньютона/невязки, принятый журнал,
скалярные пакеты, датчики, попадания/промахи кэша и обновления скалярного
шага. `newton_status_reads` учитывает чтения внутри CUDA-решателя отдельно.
`upload_bytes`/`download_bytes` — полезные данные пакетов адаптера, а не
измерение всего трафика драйвера; скалярные параметры запусков указаны
отдельно. На CPU это счётчики сериализации, а не PCIe.

Полный журнал по-прежнему включает принятые давления/расходы/скорости:
эти данные экспортируются по запросу API. Расписание, PID, выдержки защит
и скалярная координация остаются на CPU. Этот блок не объявляет нулевой
обмен CPU–GPU и не переносит старые PR/газовые модели автоматически.

В связанном тепловом расчёте добавлен прямой поток принятых тензоров
из механического ядра в тепловое (`hydraulic_heat_transfer=auto`).
Он применяется для report/interval на одном устройстве Torch. Значение
`device` требует совместимого исполнения, `host` сохраняет прежнюю передачу
через CPU для парной проверки. Недоступная CUDA не заменяется CPU.

Давления, расходы, поагрегатное тепло и переносы массы не пересобираются
на CPU для повторной загрузки тепловому ядру. Каждый принятый физический
шаг сразу обрабатывается тепловым trial-cursor; сохраняется не более двух
пакетов принятого гидравлического макрошага. Отвергнутые пробы теплового
состояния не меняют. Хеш модели проверяется при открытии окна и перед
публикацией, а не пересобирается на каждом физическом подшаге; изменение
модели внутри окна отклоняется до публикации. Публикация теплового окна
происходит после успеха
всего окна и выгрузки датчиков; ошибка не оставляет частичного состояния.
Тепловая ошибка не превращается в повтор гидравлического шага.

CPU-журнал, скалярные балансы, управление и тепловые граничные команды
сохраняются. Это не нулевой обмен с CPU. Счётчики теплового адаптера
`device_hydraulic_records` и `device_hydraulic_bytes` показывают число
и объём повторно использованных тензоров, а не измеренный трафик PCIe.
Для полного контура отдельно учитываются оба адаптера:

```bash
python scripts/benchmark_device_heat_coupling.py --device cuda:0 \
  --output results/device_heat_pair.json
```

Компактный механический журнал и дальнейшее пакетное исполнение управления
остаются отдельными этапами. Текущая оптимизация не расширяет физические
предположения жидкостной/калорической модели до многофазного EOS.

Парная проверка полного малого сценария подтвердила точное совпадение
всех журналов и снижение входного трафика теплового адаптера на 77.1%,
но **не подтвердила ускорение всей станции**: в финальной паре 214.0 →
232.6 с при изменяющейся нагрузке хоста. На короткой связанной волне
513 неизвестных получено 1.84 → 1.42 с; это отдельный единичный замер.
Подробности и ограничения:
[протокол прямого сопряжения](../reports/validation/2026-11-03/DEVICE_HEAT_COUPLING_VALIDATION.md).

## Повторно используемый граф теплового линейного шага

В обычном связном расчёте `thermal_execution=auto` использует CUDA Graph
для неизменного `TorchHeatEquations.linear_step` на CUDA. На CPU остаётся
eager. Режимы `eager` и `graph` доступны для парного сравнения; явный graph
на CPU и ошибка захвата вызывают ошибку. Ошибка не отключает проверки
и не запускает скрытый CPU-решатель.

Граф получает текущие температуры, массы, шаг, коэффициенты оператора,
границы, внешние источники и, при необходимости, LU-факторы. Пакеты
обновляются на устройстве отдельно по dtype; целочисленные перестановки
не преобразуются в float. Размер/тип входов, бюджет разреженных итераций
и вариант решающей функции входят в ключ кэша. Кэш ограничен четырьмя
графами и принадлежит одному адаптеру модели. Шаг и значения коэффициентов
не порождают новый граф.

Результат копируется из повторно используемого буфера перед следующим
replay; принятые состояния и поля истории не могут быть перезаписаны.
Вектор изменения энергии сохраняет выравнивание исходного выделения
памяти: это нужно для прежнего порядка GPU-редукций и точного совпадения
журналов даже при энергиях порядка 1e-17 Дж.

Адаптация времени, чтения её статусов, проверка каждой принятой записи,
поиск остановов и CPU-управление остаются прежними. Граф сокращает цену
запуска вычислений, а не число обязательных проверок. Диагностика теплового
адаптера дополнена `linear_graph_captures`, `linear_graph_replays`,
`linear_graph_input_bytes`, `linear_graph_input_packets`. Последние два
счётчика относятся к пакетам внутри GPU, а не PCIe/H2D.

Парный полный сценарий:

```bash
python scripts/benchmark_heat_graph.py --device cuda:0 \
  --output results/heat_graph_pair.json
```

На полном малом сценарии станции две пары с обратным порядком исполнения
дали eager 159.3/158.4 с и graph 154.1/154.0 с — около 3% по среднему.
Все состояния, энергетические журналы и события совпали точно.
Это результат конкретного наземного сценария, не замер Norne.
[Протокол графового исполнения](../reports/validation/2026-11-03/HEAT_GRAPH_VALIDATION.md).

## Выборочный механический журнал

`hydraulic_journal=compact` сохраняет все принятые скалярные балансы и
события, но не выгружает в CPU-историю полные давления/расходы/скорости и
распределённую диссипацию каждого подшага. Список
`hydraulic_journal_branches` выбирает средние расходы ветвей. Клапаны
рециркуляции добавляются автоматически; состояния PID, защит и
контрольные точки остаются полными. По умолчанию действует прежний full.

Отбор выполняется до D2H и создания Python-словарей. Это не последующее
удаление полей из уже выгруженного полного отчёта. Давления всех ячеек,
энергия и рабочие области оборудования продолжают проверяться на GPU
при каждом численном шаге. В тепловое ядро передаётся полный принятый
GPU-пакет с прежними поагрегатными проверками; неполная CPU-запись не
используется как замена распределённой тепловой информации.

Конечные координаты выгружаются один раз на физический API-интервал.
Вложенное управление может создавать много таких интервалов за один
внешний отчёт. Нулевой обмен CPU–GPU не заявляется: остаются скалярные
проверки, датчики и полные конечные состояния. Диагностика механического
адаптера дополнена `endpoint_download_batches/bytes`. GPU-селекторы
ветвей/relief имеют ограниченный кэш четырёх вариантов.

Compact требует Torch interval и, для тепловой станции, report с прямым
сопряжением на одном устройстве. Несовместимый путь явно отклоняется.
При необходимости полной пространственной истории используйте full;
температурная история управляется своей опцией.

```bash
python scripts/run_thermal_liquid.py configs/surface_thermal_liquid.json \
  --device cuda:0 --hydraulic-journal compact \
  --hydraulic-journal-branches line p1 --output results/compact_station.json
```

Парная квалификация сравнивает полные конечные состояния и **все
сохраняемые** записи, включая тепловые/управляющие журналы. Отдельный
тест сравнивает невыгруженные GPU-поля каждого принятого шага. Хеш
проекции full сравнивается с compact; сырой хеш двух разных форматов
журнала не объявляется одинаковым.

В квалификационном полном сценарии механическая выгрузка уменьшилась
на 31.46%, JSON принятых шагов — на 35.15%. Спокойная обратная пара дала
155.7 → 153.4 с (около 1.5%); первая пара шла при меняющейся нагрузке.
Короткая волновая задача с 2049 неизвестными показала более сильный эффект
выгрузки, но этот результат не переносится на всю станцию или Norne.
[Протокол компактного журнала](../reports/validation/2026-11-03/COMPACT_JOURNAL_VALIDATION.md).
