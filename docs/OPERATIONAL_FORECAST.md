# Эксплуатационный прогноз: пласт и установившаяся наземная сеть

Для длительного прогноза используется существующий `coupled_facility`:
black-oil FIM → скважины ↔ установившаяся сборная сеть → сепарация →
водяная сеть и газовый экспорт. Собственная акустика сантиметровых PR-ячеек
не включается в каждый шаг прогноза. Подробный PR-граф сохраняется для
отдельных быстрых переходных задач; автоматически эти модели не подменяются.

## Что действительно связано

`SurfaceCoupledBlackOilWells` включает противодавление физической сборной
сети и перекрёстные производные скважин в FIM. `FacilityCoupledFIM`
проверяет фактическую компонентную добычу на ограничениях сепараторов,
водяной сети и газового экспорта. При нарушении ограничений повторно
решается тот же пластовый шаг с общим множителем уставок добывающих.
Выбранный режим заново рассчитывается и только затем принимается;
готовая добыча не масштабируется задним числом. Неуспех возвращает
физическое состояние и накопления к началу пробного шага.

Это существующее внешнее сопряжение по общему ограничителю добычи,
а не новый монолитный Якобиан всего промысла. Первый допустимый вариант
требует одного пластового решения; ограниченный режим может потребовать
много проб. Время проб необходимо учитывать в полном измерении.

## Расписание эксплуатации

`run_fim_blackoil_surface.run_case(..., facility_schedule=[...])`
поддерживает события с `time_days` и `controls`. Время — от начала
запуска; события строго возрастают и лежат в `[0, days)`.
Ни один отчётный интервал и принятый пластовый подшаг не пересекают
момент команды. После события адаптация шага продолжается существующим
интегратором `Simulator.run_step`.

Каждое событие полностью заменяет операторские команды:

```json
[
  {"time_days": 0, "controls": {}},
  {"time_days": 10, "controls": {"gas_valve_max_opening": 0.8}},
  {"time_days": 20, "controls": {}}
]
```

Пустой словарь возвращает настройки оборудования из модели. Набор
поддержанных команд определяется `FacilityCoupledFIM.control_fields`;
произвольное масштабирование подачи запрещено. События применяются
на границе интервала; мгновенная переходная реакция оборудования
между установившимися состояниями в этом режиме не разрешается.

`report_days` задаёт максимальную длину запрашиваемого отчётного
интервала; события дополнительно разрезают его. Без явно заданного
`max_time_step_days` этот интервал также ограничивает шаг FIM согласно
существующей политике симулятора. Для точности во времени нужны
сравнение с более частыми шагами и согласованные допуски, а не только CNV/MB.

## Запуск и проверка

Из корня проекта; каталог результата должен отсутствовать:

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 PYTHONPATH=src:scripts python scripts/run_fim_facility_forecast.py --schedule configs/fim_facility_forecast_schedule.json --days 30 --report-days 5 --device cpu --output /tmp/forecast_month
PYTHONPATH=src:scripts python scripts/check_fim_facility_forecast.py /tmp/forecast_month/trajectory.json.gz
```

Для CUDA требуется явно выбранный `CUDA_VISIBLE_DEVICES`. Этот драйвер
не превращает существующую CPU-арматуру и весь facility-код в GPU-код.
CPU-замеры нельзя объявлять подтверждением CUDA-производительности.

Протокол сохраняет исходные хеши, расписание и длительность. Траектория
с фактическими расходами, уставками, командами, балансами и статистикой
адаптации записывается до независимого учётного аудита. Только полный
прошедший проверку расчёт получает `summary.json` со статусом `complete`.
Незавершённая серия остаётся помеченной `incomplete`.

Проверяющий независимо суммирует материал принятых скважинных потоков,
подачу и экспорт; сверяет расписание, часы, применённые ограничения и
сквозную убыль запасов. Он не запускает решатель и не подменяет
независимую проверку физических корреляций/PVT. Массовый бюджет аудита
не меняет критерии Ньютона или интегратора.

## Область применимости существующего режима

Сборная сеть — дерево с однородной black-oil моделью без проскальзывания,
одной PVT-областью и ограничениями направления/геометрии труб.
Текущий facility-драйвер поддерживает активные добывающие скважины
с положительными уставками дебита; нагнетание и полный останов скважин
этим сценарием не квалифицированы. Газовый экспорт использует существующую
модель сухого идеального газа. Нефть учитывается в продуктах сепарации;
произвольная гидравлическая сеть её дальнейшего экспорта здесь не решается.
Это не эквивалент всей подробной PR-наземной сети.

Следующие расширения: проверка временной точности и масштабирования,
нефтяная экспортная и нагнетательная ветви, более общий состав/термодинамика
и топология, затем согласованное подключение выбранной эксплуатационной
динамики. Многолетний Norne с полной наземной инфраструктурой остаётся
отдельным приёмочным сценарием.


## Границы PVT в пробах мощности

Если при заданном пробном расходе требуемое давление конца трубы выходит
за пределы общей PVT-области, `BlackOilPipe` выдаёт отдельное
`PipePressureCoverageError`. Внешний facility-поиск отмечает только эту
пробу как недопустимую и может проверить меньшую уставку. Запасы и
накопленная добыча отвергнутой пробы откатываются. Путь отражается в
`trace` с причиной `pipe_pressure_coverage`.

Это ограничение области модели, а не доказанное физическое запирание
потока. Свойства не экстраполируются, таблица не расширяется молча.
Обычные ошибки PVT (`PropertyModelError`) по-прежнему прерывают расчёт;
исчерпание численного бюджета поиска давления относится к
`HydraulicConvergenceError`, а не к выходу за PVT-область.


## Подтверждённый сценарий и следующие расширения

Для маленького связанного пласта проверен месяц с ограничением и
восстановлением газового экспорта. Сравнение 5-суточных интервалов с
суточными дало 0,513% по накопленной компонентной добыче и 148 Па по
конечному давлению. 10-суточный вариант не прошёл заранее заданный
бюджет добычи 1%. По умолчанию драйвер запрашивает 5 суток;
это начальная настройка, требующая проверки для конкретной модели.

Отдельный месячный запуск на 32×32×1 ячеек завершён с проверкой балансов.
Это ограниченный связанный пример с двумя скважинами, не подтверждение
скорости полного Norne или произвольной сети. Измерения и полные
траектории — [в протоколе](../benchmarks/reports/surface_operational_forecast/README.md).


## Ускоренный ограничитель и опциональная адаптация времени

Связанный годовой опыт дополнительно проверен на CPU и RTX 3090 Ti:
те же 365 суток и шесть событий, одинаковые исходники и конфигурации,
проверены поля и все общие отчётные даты. Месячные пары расширены до
65 536 ячеек / 64 скважин и отдельного сильно истощаемого пласта.
Пакетная сборная гидравлика выполняется на CUDA, малая площадка и
управление по-прежнему используют CPU. В повторных пробах сохраняется
уже допустимое BHP, вместо ненужного принудительного увеличения drawdown.
Новый критерий готовности артефактов включает завершённый progress,
отсутствие маркера ошибки и checksum траектории. Отказ аудита после
интегрирования записывается с этапом; достижение конца времени само
по себе не означает успешной квалификации.

Совпадение устройств не заменяет временное уточнение. В сильном истощении
шаг 5 суток не прошёл сравнение с 2,5 суток: разность конечных накоплений
до 3,45%, на промежуточных датах до 7,43%. Адаптивные диагностические
пробы потребовали большого числа подшагов и не объявляются принятыми.
[Протокол, память, численные бюджеты и точные границы](../benchmarks/reports/surface_gpu_year/README.md).

По умолчанию `control.search_method=safeguarded` выбирает пробы по
измеренным запасам до ограничений, с возвратом к делению пополам.
Контрольный `bisect` сохранён. Вычисленная допустимая/недопустимая
скобка и абсолютный допуск проверяются независимо по trace.
Опциональный `facet_safeguarded` сопоставляет остатки одного и того же
ограничения между границами; правила приёмки физической пробы прежние.

Launcher `run_fim_facility_forecast.py` сохраняет RSS и swap процесса
в прогрессе и итоговом `host_memory`. На Linux можно задать
`--host-memory-limit-mib 2048`: сумма RSS+swap проверяется до построения
модели и после принятых стадий. Превышение записывает `failure.json`,
а не успешный результат. Это реактивная проверка, не жёсткое ограничение
выделений внутри одной стадии. Пик RSS относится ко всей жизни процесса,
включая импорты и сериализацию, память Torch CUDA учитывается отдельно.

Для приёмки временного уточнения используйте
`scripts/check_facility_refinement_pair.py candidate reference --budgets budgets.json --output comparison.json`.
По умолчанию требуются завершённые 30 суток, неизменённые исходники/PVT,
checksum траекторий, более строгая временная политика, фактически больше
принятых стадий, материальный аудит и сравнение полей/историй скважин.
Для короткого опыта горизонт нужно объявить явно через `--required-days`.

Необязательный `coupled_facility.time_control` ограничивает изменение
фактических компонентных дебитов и старт после операторского события.
Это дополнение к существующему управлению шагом FIM, не строгая оценка
его ошибки. Оно может дать меньшую погрешность ценой большего числа
шагов; отсутствие поля сохраняет обычную временную политику.
[Подробная постановка](FACILITY_SEARCH_SCALING.md).
[Актуальная серия скорости и точности](../benchmarks/reports/surface_capacity_search/README.md).

Для оценки локальной ошибки интегрирования добавлен отдельный
`coupled_facility.temporal_control`. Он сравнивает полный шаг backward Euler
с двумя половинными решениями всего связанного контура, включая повторный
поиск ограничений площадки. Принимаются два половинных состояния и их
собственные интегралы отборов; грубое решение в материальный баланс не входит.
Проверяются давление, независимые насыщенности Sw/Sg, Rs/Rv и интегралы
компонентных отборов. Значение любого нормированного дефекта выше единицы
отклоняет весь интервал с восстановлением пласта, скважин и учёта площадки.
Предложение следующего шага и сокращение отклонённого шага используют
квадратный корень измеренного дефекта. События по-прежнему разделяют шаги.

`temporal_control` и прежний `time_control` одновременно задавать нельзя.
`withdrawal_error_scale="cumulative"` нормирует дефект интеграла отбора
на накопленную добычу компоненты, а не только на приращение текущего
макрошага. Числитель и абсолютный допуск прежние. Все принятые массы
остаются суммой фактических половинных стадий; грубый интеграл отбрасывается.
Такой режим контролирует интегральное состояние прогноза и требует
собственного независимого уточнения. Прежний `increment` сохраняется
по умолчанию. Аудитор восстанавливает начало макрошага из материальной
истории и проверяет масштаб, грубый интеграл и нормированный остаток.
Для контроля интегрального прогноза есть отдельный режим
`temporal_control.withdrawal_error_scale="cumulative"`. Он оценивает
разность отборов полного/половинных решений относительно накопленной
добычи, а не только приращения за один короткий шаг. Относительный
масштаб — максимум модулей двух накоплений; абсолютный допуск остаётся.
Прежняя нормировка на приращение называется `increment` и сохранена
по умолчанию. Смена режима не ослабляет CNV/MB или ограничения площадки,
но меняет временную сетку и требует отдельной глобальной приёмки.
Опциональный `temporal_control.well_bhp_tolerance_pa` добавляет в дефект
забойные давления всех скважин. По умолчанию выключен; положительное
значение в Па сравнивается с максимумом разности конечных BHP полного
и двух половинных решений. Все давления уже есть в отчётах. Отклонение
восстанавливает тот же снимок пласта/скважин/площадки; новые решения
ради измерения BHP не добавляются. Аудит требует соответствующий остаток
и исходные BHP грубой оценки. Этот локальный критерий также требует
отдельного подтверждения глобальной точности.
Новая опция оценивает локальную погрешность, а не гарантирует заданную
глобальную точность многолетнего прогноза. Она требует одного дополнительного
полного решения к двум принимаемым половинным; стоимость всех проб,
включая отклонённые, сохраняется в `temporal_work`. Аудит отдельно учитывает
грубые оценки на принятых интервалах и проверяет пары фактических стадий.
Точность внутреннего поиска уставки должна быть существенно выше требуемой
временной точности, иначе разности решений содержат шум этого поиска.

Для повторных проб доступно `physical_surface_network.bhp_initialization =
"rate_network"`: начальное BHP предсказывается по аффинному закону притока
при замороженных свойствах ячеек. Гидравлическая проверка отбрасывает
недопустимое приближение; ошибки свойств не подавляются. Допустимое решение
сети повторно используется только при точном совпадении расходов и объекта
сети. Значение по умолчанию `"previous"` сохраняет прежнее поведение.
Предиктор не меняет физические уравнения и допуски Ньютона, но может менять
последовательность адаптивных шагов, поэтому его скорость нельзя оценивать
без проверки временной точности.

Начальная квалификация нового контроля выполнена на коротком переходном
интервале 0,02 суток для 1024 ячеек / 16 скважин. Более строгая пара
прошла прежние глобальные бюджеты: давление 9,69 Па, Sg 7,05e-6,
накопления 0,0139%; исходный более грубый вариант по Sg отвергнут.
Цену 130 / 248 половинных стадий и 252,52 / 421,10 с CPU нельзя
выдавать за быстрый месячный прогноз. На отдельном 30-суточном случае
65 536 ячеек / 64 скважин предиктор BHP сохранил поля и накопления.
Короткая двухскважинная пара нового контроля на CPU/CUDA также прошла.
[Протоколы, отвергнутые варианты и точная область приёмки](../benchmarks/reports/surface_time_accuracy/README.md).

Для сокращения повторных решений добавлен
`coupled_facility.control.commit_method="state_restore"` (по умолчанию
остаётся `replay`). Он принимает сохранённое состояние уже рассчитанной
допустимой пробы текущего интервала. Поиск скобки, допуски, реальная
проверка оборудования и учёт отборов сохраняются. Снимок не содержит
плотной пластовой матрицы и не используется как физическое решение
другого шага. На точном переходном опыте 130 принятых стадий совпали
с контрольным повтором, число проб сократилось с 1609 до 1414.
[Цена, исходники и ограничения сравнения](../benchmarks/reports/surface_coupled_cost/README.md).


## Представление чувствительностей сборной сети

По умолчанию используется плотная таблица `sensitivity_backend=dense`.
Опция `physical_surface_network.sensitivity_backend=tree_operator`
заменяет её компактным оператором и извлекает только нужные производные
скважин. Физическая модель и интегратор не меняются; при стандартном
`well_block_backend=dense` полные B/D сохраняются. Опциональный
`well_block_backend=tree_structured` исключает их по структуре дерева
и допускает больше 128 скважин по ресурсному бюджету.
[Метод и квалификация](STRUCTURED_WELL_COUPLING.md). Активный регулятор давления требует отдельного расширения,
поэтому такой набор опций явно отвергается.
[Единицы, API и область подтверждения](TREE_PRESSURE_TANGENT.md).

Опциональная пакетная гидравлика выбирается внутри
`physical_surface_network.network`: `hydraulic_backend=torch_batch`,
`pipe_batch_size=128`. Она не меняет временную политику и сохраняется
при статических управлениях площадки. По умолчанию используется `scalar`.
[Метод, измерения и границы](BATCHED_BLACKOIL_HYDRAULICS.md).

## Годовой связанный CPU-сценарий

Проверены 365 суток на 32×32 ячейках и 16 скважинах со сборной сетью
и квазистационарным оборудованием. Интервалы 10/5 суток дали 69,9/109,5 с
CPU, 37/73 принятых подшага, без численных отказов. Пройдены конечное
сравнение и 37 общих отчётных дат с интегралом фактических отборов.
[Конфигурация, допуски и границы](../benchmarks/reports/surface_year_forecast/README.md).

`run_case(..., progress_callback=...)` опционально сообщает о завершённых
интервалах. Driver сохраняет атомарный `progress.json` и итоговый
`complete` после успешного аудита; это не checkpoint физического состояния.
`check_long_facility_trajectory.py` сравнивает расходы, BHP и накопленные
компоненты на общих отчётных датах, включая все принятые подшаги интеграла.
